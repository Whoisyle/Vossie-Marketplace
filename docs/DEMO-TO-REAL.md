# Demo behaviour that must become real

Everything below works in the app today only as a demo. Nothing here is connected to a real provider, so none of it may be described to users as live. Work through this list before release. Keep it up to date: add a line when something new is built as a demo, tick it off when it is real.

Last updated: 2026-10-20.

## Backend and accounts

- [ ] **Hosted Supabase project has the OLD schema.** The new migrations in `supabase/migrations/` are written and tested (PGlite) but not applied. Owner runs `supabase/scripts/apply-hosted.cjs` with the database password (it deletes the old tables). Then deploy Edge Functions, set secrets, enable the auth hook.
- [ ] **Sign-in is a demo.** Any email signs in without a password. Real sign-in is an email one-time code through Supabase Auth (`EXPO_PUBLIC_USE_BACKEND=true`), which needs email sending set up in the Supabase project. Eduvos single sign-on is not available yet.
- [ ] **Student number record is mock** (`src/data/studentRecord.ts`). Real value must come from Eduvos.
- [ ] **Screens run on the in-memory demo store.** Wire each screen to `src/services` (buyer side not wired yet).

## Money

- [ ] **No payment provider.** Card, Apple Pay, Google Pay, Instant EFT and the wallet top-up are all mock flows. A payment provider is not chosen. Apple Pay and Google Pay also need a development build and merchant setup.
- [ ] **Withdrawals and payouts do not move money.** Needs the provider's payout API and bank-account verification.
- [ ] **Vouchers, points, subscriptions and tips are demo rules** held in the app; the database versions exist but are not applied.

## Seller mode (added 2026-10-20)

- [ ] **Seller verification is automatic.** Documents move Pending, In review, Verified on a timer. Real review is by Vossie Operations: documents upload to Supabase Storage and staff approve in the staff app / Supabase dashboard. The staff app does not exist yet.
- [ ] **Document uploads are not stored.** Needs the storage bucket, signed upload URLs and a virus/size check.
- [ ] **Seller identity checks (ID, proof of address, CIPC registration) are not verified** by anything.
- [ ] **Seller orders come from the demo loop**: a buyer's order on the same device appears in the seller's Orders. Real orders arrive through `seller_orders` with realtime updates.
- [ ] **Order alerts are local.** Real alerts need push notifications (Expo push plus a server trigger).
- [ ] **Seller Earnings and the weekly chart are computed from demo orders.** Real numbers come from the money ledger.
- [ ] **Handoff code check** runs against a demo code. Real check is `seller_complete_handoff`.
- [ ] **Seller messages** use the demo conversations; real ones use `messaging` services and realtime. The thread page is the buyer's look.
- [ ] **Demo orders arrive on a timer** while a seller is in seller mode (`SellerDemoEffects`, 40, 110 and 200 seconds). Remove once real students order.
- [ ] **Listing photos:** seller listings use our drawings; real photo upload is not built, and the database will not publish a listing without a photo. Deleting a listing is local only (no archive function).
- [ ] **Seller payouts and bank details:** the saved bank keeps the last four digits only and nothing is verified with the bank.
- [ ] **Platform fee on sales** is a demo 5% (`PLATFORM_FEE_PERCENT` in `src/seller/state.ts`), shown on the order and taken from earnings on the phone only. The real fee policy is an open decision and must be taken by the database when an order completes.
- [ ] **The seller screens' live path** (Supabase) is written and tested against mocks and the database tests, but has never run against the hosted project, because the migrations are not applied. First run needs a real sign-in (email one-time code), a staff account to approve documents, and a listing photo.
- [ ] **Courier handover (seller side)** is a demo: a courier "Tebogo K." takes a ready delivery 5 seconds later (`SellerDemoEffects`), the four digit handover code is made on the phone, and confirming pays the seller straight away. Real: a courier job, a code checked on the server, and payment only after delivery. The buyer is told it is on its way, but there is no courier app yet.
- [ ] **Seller Promotions, Reviews, Returns and disputes, Team members and notification setting** live on the phone only (no tables yet). Real needs promotions with redeemable codes at checkout, buyer reviews and replies, refunds that move money, team invites by email with a packer role, and saved settings. Analytics conversion (4.2%) is a fixed demo figure.
- [ ] **Stock steppers and Archive** call the same listing save as Restock in live mode; the database has no archived state, so Archive pauses the listing there. Product photos (up to 6) and variants stay on the phone until upload and options are built.
- [ ] **Store preview Share** only shows a message; there is no public store page or link.
- [ ] **Operating times** (presets, lecture timetable, closures, pickup slots, queue-when-closed) live on the phone. The database holds one open range for all days (`opens_at`, `closes_at`, `open_days`), so per-day hours, lectures and closures need new columns or a table. Buyers do not yet see Open or Closed, hours or "Back on", checkout does not offer the pickup slots, and orders that arrive while closed are queued only in the seller's own list.
- [ ] **Transactions, receipts and statements** are built from the demo ledger. Share sends plain text (or copies it on the web); a signed PDF receipt, reference numbers from the server and real monthly statements need the money ledger.
- [ ] **Notification preferences** (push and email per kind, quiet hours, sound) are saved on the phone and do not yet change what is sent. Real push needs Expo push tokens and a server trigger; email needs a sender.
- [ ] **Security page** reuses the buyer's Face ID, two-factor and login-activity state. Sign-in email cannot be changed (Eduvos owns it). The list of signed-in devices is the demo list.
- [ ] **Account settings:** tax number is kept on the phone only; Download my data and Close seller account do nothing on a server.
- [ ] **Reels:** a seller's live reels now appear first in the buyer's Reels feed, and a buyer's like counts for the seller. The picked video is not uploaded or played (only the product poster shows), and views, taps and sales driven are still demo numbers that grow on a timer. Real reels need video storage and event counts from buyers.
- [ ] **Seller plans:** Free, Seller Plus (R49) and Seller Pro (R99) are demo prices and limits (10 products on Free; 0, 5 and unlimited live reels; analytics tabs; fees 5%, 3% and 2%). Plans are bought with the buyer wallet through the existing subscription flow. The database has the Seller Plus plan row (migration `20261021000100_seller_plus_plan.sql`, not applied to the hosted project) but does not enforce the limits or the fee by plan.
- [ ] **Analytics conversion (4.2%)** is a fixed demo number, and product and reel analytics come from the demo orders and reels.
- [ ] **Store location and maps:** the place search and pin lookup use the public OpenStreetMap service (Nominatim), which has a fair-use limit and no promise of uptime. Production needs a geocoding provider with a key (or our own). The two campus hubs are real places, but the Eduvos pin is placed by the two streets Eduvos publishes (12 Esselen Street, cnr Steve Biko) and should be moved to the exact gate once the owner confirms it. The place is saved on the phone and shown on the buyer's store page map; the database still holds only a text location. Order drop-offs on the map are found from the typed address and may be wrong or missing.
- [ ] **Store banner, product photos, support attachments and documents** are kept on the phone and not uploaded. The documents screen takes files from the photo library, the camera and Files (Files on a phone needs `expo-document-picker`; the web build uses the browser chooser). There is no scan option (removed at the owner's request).
- [ ] **Packages:** `expo-video` and `expo-document-picker` are installed (fetched from the registry with their checksums verified, because `npm install` refuses the registry certificate while the PC clock is wrong; run `npx expo install --check` once the clock is right). `expo-notifications` is still not installed, so push cards are in-app only and the app badge is not set on the phone's icon.
- [ ] **Listing details, extra photos and the reviews on each product page are written for the demo** (`data/mock/productDetails.ts`, `stockReviews.ts`, up to three photos per product). Real listings carry the seller's own description, details and photos, and reviews only from students who bought. The "You may also like" rows are simply the same category for now; real ones need the recommendation query.
- [ ] **Reel videos and product photos are bundled stock media** (Mixkit clips and Pexels photos, both free to use) so the demo looks real. A seller's own picked video plays on their phone only; real reels need upload to video storage, and real products need the seller's own photos in storage.
- [ ] **Help and support:** requests are kept on the phone and Vossie support answers 7 seconds later by a demo timer. The email address and phone number on the page are placeholders. Real support needs a ticket table, staff replies, attachments in storage and notifications.
- [ ] **Promotions** apply at the buyer's checkout for the store the student runs: a code typed in the voucher box, or an offer with no code applied by itself (percent, rand off, free delivery when the whole cart is that store's, buy X get Y, bundle price), with start and end dates, minimum spend, first order only, total and per-student limits. Uses are counted on the phone. The live version must price offers on the server and count uses in the database.
- [ ] **Share store:** the web link (vossie.app/s/...) is a demo address. The QR code holds a Vossie app link (vossie://home/store/<id>) which opens the store in the app for anyone who has it.
- [ ] **Seller wallet:** the balance card, payout cards and transactions are the seller's earnings, shown like the buyer's wallet. Payout cards are the buyer's saved cards; paying out to a card or by instant EFT is a demo.
- [ ] **Push notifications:** the cards, their buttons (Accept, Decline, Restock, Reply, View), quiet hours, sound and the per-kind switches all work inside the app, and the heads-up slides in when an alert arrives while the app is open. Real push on a locked phone needs `expo-notifications` (not installed: npm refused the registry certificate on this PC), Expo push tokens saved per seller, a server trigger for each event, and the notification action buttons registered with the phone. Email delivery of the same alerts needs a mail sender.
- [ ] **Analytics:** the charts are interactive (drag across the line and bars, tap the ring, the grid and the funnel). Their numbers come from the demo orders, ledger and reels. New and returning buyers are matched by name, which is not reliable; real analytics need buyer ids and event tracking for views and taps on products.
- [ ] **Store preview** is built from the seller's own data and the buyer's own components, and the buyer's store page now reads the same data (name, words, banner, logo, pickup place and map, open or closed, offers, products with stock, reviews with the seller's replies, follower count).
- [ ] **Verified documents** can be viewed and replaced; the new file is re-checked by a demo timer. The Eduvos student card has no file to show, only the record.
- [ ] **Order tools on paid plans:** order search, accept all and the auto-accept rule (Plus), and returning-buyer flags with a thank-you offer (Pro) run on the phone from the demo orders. Auto-accept only works while the app is open; the live version must run on the server so it works when the phone is off. Offers made to returning buyers create a promotion code but nothing is sent to the buyer yet.
- [ ] **Weekly goal, close early today and the weekly summary** are kept on the phone. The summary is sent the first time the app is opened in a new week, not on Monday at 08:00, and weekly statements are built from the demo ledger.
- [ ] **App icon number** counts unread alerts plus orders waiting. It needs `expo-notifications` to show on a phone (not installed; see the clock problem above).
- [ ] **New order offer from the bottom** and the buyer's new notification cards work inside the app only. The 30 second ring only puts the card away; the order stays New.
- [ ] **The loop between buyer and seller runs on one phone.** The student's own store replaces the demo store it took over, so buyers see its products (published, in stock) and can order them; orders take stock off; a closed store shows the buyer a note and the order queues; reviews, returns and problems, follows and messages the buyer sends land with the seller, and the seller's replies, refunds (paid back to the buyer's wallet) and answers go back. In the live app all of this is rows in the database that both sides read, with the buyer's and the seller's phones separate, and money moved by the server.
- [ ] **Returns and refunds:** a refund goes straight to the buyer's demo wallet when the seller approves. Real refunds need the payment provider, the seller's balance check, and the dispute rules (windows, evidence, support escalation).

## The courier app (built 2026-10-21)

- [ ] **Courier review and verification** is the demo's: documents are not stored anywhere and the checks clear one by one on a timer (about 15 seconds). Real review needs the documents in storage, an Operations queue, a real background check, and the Operations approval writing `status` to the database.
- [ ] **The Courier Login screen** (phone and password, for a courier on a new phone) is not built: in the demo a courier is a student account that switched role. Real couriers who are not students need their own sign-in.
- [ ] **Jobs:** a delivery order a buyer places with a Vossie courier becomes a real job for a courier approved on the same phone when the seller marks it ready. Without one, the demo courier "Tebogo" still takes it. Three labelled **demo jobs** appear the first time a courier goes online so the list is never empty; they show both codes because no seller or buyer app is behind them. Real jobs must be offered by the server to couriers near the store, with the countdown and re-offer rules enforced there.
- [ ] **Codes:** the pickup code is the seller's four digits (read out to the courier), the delivery code is derived from the order and shown to the buyer, and the return code is shown on the courier's phone for the seller to type. In the demo they are computed on the phone; real codes must be made and checked by the server so a courier cannot work them out.
- [ ] **Position:** the courier's position on the map is simulated (a ride of about 45 seconds) and the buyer's tracking reads the same number. Real positions come from the courier's phone while the job is active, with the arrival slide checked against the drop-off by the server.
- [ ] **The 10 minute wait** at the door before an unreachable buyer can be reported is shortened to 20 seconds in the demo.
- [ ] **Pay:** a delivery pays the buyer's delivery fee, which is a base R20 plus R6 a kilometre (capped at R60) once the buyer has pinned the address on the map, and the flat R15 until then. Vossie covers the fee on Plus members' free deliveries. Cash out and the weekly Friday payout are not connected to a bank or a payment provider; the bank details are only text. Tips come from the buyer's rating and are 100% the courier's.
- [ ] **Failed deliveries:** after two tries the parcel goes back; when the seller types the courier's return code the buyer is refunded the items to their wallet (the delivery fee is kept), the stock goes back and the courier is paid for the trip. A real refund needs the payment provider and the dispute rules.
- [ ] **Support and SOS:** SOS opens an urgent case and shows real emergency numbers that really dial, but Vossie Operations is not connected, so nothing reads the case or the shared location yet. The "Case #S-118" numbers are local counters.
- [ ] **Messages with the buyer** use the same thread the buyer sees under their order. Messages to the seller from the courier are not built (the courier can call the seller).
- [ ] **Performance, level, badges and streak** are worked out on the phone from the courier's own jobs. The demo gives a courier an experienced past the first time they are approved (86 deliveries over a month, a 4.9 rating, tips, payouts, a saved FNB account and feedback), all invented, so every page has something in it; the deliveries the app makes add to it. The real score, level and streak must be computed on the server from real jobs, and a new real courier starts with nothing.
- [ ] **Packages:** `expo-video` and `expo-document-picker` were installed from the registry with their checksums verified, because `npm install` refuses the registry certificate while the PC clock is wrong. Run `npx expo install --check` once the clock is right.
- [ ] **Courier checks are format checks only.** The courier does not type an ID number (only a photo of the ID document, which Operations reviews); the number plate must look like a South African plate (provincial, Western Cape or KwaZulu-Natal forms); the make and model come from a list of cars and scooters sold here; the colour comes from a list; the driving licence number must be 10 to 13 letters and digits; the licence expiry must be in the future and within five years. Nothing asks the national records (NaTIS, Home Affairs, eNaTIS) whether the person, the plate or the licence is real. That needs a verification provider and Vossie Operations reviewing the documents.
- [ ] **Zones differ by campus** (the campus plus two nearby areas for each of the 12 campuses, with approximate positions), and a courier can add a place by searching OpenStreetMap. Offers whose pickup is more than about a kilometre from every zone that is on, or longer than the courier's longest trip, are hidden (with a notice). The real offer matching must be done on the server.
- [ ] **Busy areas and bonus offers** are demo: demand follows the time of day with a small variation per zone, and one demo offer carries a busy-area bonus. Real demand must come from the orders being placed, and bonuses from Vossie's rules.
- [ ] **Weekly goal, streak and statements** are worked out on the phone from the courier's earnings and jobs. Statements are lists on screen; there is no PDF or emailed statement yet.
- [ ] **Chat with the seller** at pickup writes into a thread the seller sees in Messages (and the seller's reply shows to the courier). It only works for a real job; a demo job has no seller. Messages are not stored on a server yet.
- [ ] **Referral:** the courier's share button works, but the reward for a friend who delivers is not tracked.

- [ ] **Backend status (2026-10-23):** the schema is now LIVE on the hosted project `elrqoyiegcnnjmjnjlja`: 16 migrations applied (identity, catalog, money, orders, payments, fulfilment, security policies, subscriptions, seller onboarding, courier onboarding and a search-path fix), 84 tables all with row level security, 12 campuses, 5 categories, 4 plans, 6 storage buckets. The older first schema (11 empty tables) was moved into a private `legacy_v1` schema, nothing deleted. 83 database tests pass locally. The hosted migration versions are timestamped 20261022 and 20261023 (the dashboard stamps them), so the file names in `supabase/migrations` differ from the hosted history; do not run `supabase db push` without reconciling them first. **The app still reads and writes its own on-phone demo state**; moving each role onto these functions is the next build step, one role at a time. Open items: the sign-up hook (`hook_before_user_created`, demo domain only) must be switched on in the Supabase dashboard under Authentication > Hooks, otherwise anyone can sign up; `wallet_demo_topups` is on, so any signed-in user can add demo money, switch it off before real money; the old sign-up trigger from the first schema is still on `auth.users` (harmless, it does nothing when the profile exists) but should be dropped from the dashboard SQL editor by the project owner; three advisor errors about security definer views are by design (they hide columns on purpose); handoff codes are only reachable through functions.
