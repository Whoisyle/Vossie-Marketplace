VOSSIE / DEVELOPER GUIDE
CHAPTER 01
How to use this developer blueprint
DESIGN PROPOSAL / SEPTEMBER 2026
005
DELIVERABLE BOUNDARY
This is the implementation design for the 177-screen Vossie atlas, not a
completed marketplace. It supplies architecture decisions, domain boundaries,
proposed database and API contracts, delivery sequencing, operational
requirements and a screen-by-screen build specification. The source package
contains planning data and illustrative code fragments; it is not a runnable
production backend.
READ IN THIS ORDER
Read the architecture and transaction chapters first. Implement the walking
skeleton and one end-to-end product flow. Then use the screen implementation
appendix alongside the UI/UX PDF. The motion catalogue M01-M30 is the
interaction contract. The HTML motion lab demonstrates selected behaviours with
local simulated states.
SOURCE PRECEDENCE
The five supplied Hack Jam / UX / technical PDFs and presentations are the
research baseline. The later technical dossier governs variable fees, service
authorisation and transfer operations. The 177-screen decomposition and
contracts are proposals. Earlier fixed 2% fees are not adopted. The original
custom logo must be supplied as an approved vector; text labels in engineering
prototypes are stand-ins.
DECISIONS STILL REQUIRED
Confirm pilot campuses and hubs, identity integration, payment provider
capabilities, funds custody model, fee schedule, food handling rules, data
retention, hosting region and support ownership. The engineering design isolates
these as adapters and versioned policy rather than inventing live capabilities. No
real-money pilot starts with unresolved money-flow decisions.

VOSSIE / DEVELOPER GUIDE
CHAPTER 02
Recommended stack and platform split
DESIGN PROPOSAL / SEPTEMBER 2026
006
MOBILE AND WEB
Use TypeScript. React Native with Expo and Expo Router serves iOS/Android
buyers, sellers and couriers. Use Next.js App Router for responsive buyer web
and the staff console. Reuse schemas, query contracts, tokens and domain
helpers across clients; maintain native and web UI adapters where interaction
differs. Expo Router supplies file-based navigation [D1]; Next.js separates server
and interactive client components [D8].
API AND WORKERS
Use a NestJS modular monolith with REST /v1, OpenAPI and an authenticated
WebSocket gateway. Run a separate BullMQ worker process backed by Redis.
Keep the API stateless; both processes use the same versioned domain
packages. Start with one deployable backend codebase, not independent
microservices.
DATA AND IDENTITY
Use PostgreSQL with PostGIS, SQL migrations and Drizzle for typed access.
Supabase is the proposed managed Postgres, Auth and private Storage host.
Keep marketplace mutations behind NestJS; Supabase Auth authenticates
identities, but NestJS and database constraints enforce marketplace authority.
Redis is a cache/queue, not the order or wallet source of truth.
MOTION AND DESKTOP
Use Reanimated plus gesture handling for native UI and CSS transforms for web.
Use Three.js only for optional web 3D after the CSS/SVG baseline is accepted.
Native launches with static or layered 2.5D versions. The research mentions Tauri
desktop; defer that wrapper until an actual scanner/printer or offline desktop
requirement justifies another release surface.

VOSSIE / DEVELOPER GUIDE
CHAPTER 03
System topology and deployment boundaries
DESIGN PROPOSAL / SEPTEMBER 2026
007
REQUEST PATH
Mobile / Next.js -> TLS edge -> NestJS API -> application service -> transaction
-> PostgreSQL. A committed transaction stores an outbox event. A worker
publishes notifications and integration jobs. A WebSocket notification tells
subscribed clients to refresh the affected versioned resource.
SERVICES TO PROVISION
Provision separate development, staging and production identity projects,
databases, buckets, Redis instances and provider credentials. Recommended
pilot deployment: containerised API and worker on a managed container platform;
Next.js on a Node-compatible host; managed Postgres/Auth/Storage. Select
region and contractual data handling before provisioning production. Keep API,
database and Redis near one another.
RUNTIME BOUNDARIES
API replicas must not depend on local filesystem or in-memory offer ownership.
Use private object storage for evidence and media. WebSockets need long-lived
connection support; workers need continuous execution. Do not run durable
timers or background work as untracked tasks inside short-lived web requests.
SCALE ONLY FROM EVIDENCE
Scale API replicas by latency and utilisation; workers by queue age and provider
rate limits. Add read replicas or search infrastructure only after query profiling.
Critical mutations always use the primary transactional database. Separate
services later only when team ownership or measured bottlenecks require it.
IMPLEMENTATION FLOW
Mobile / Web
API + guards
DB + outbox
Worker / provider
Event / refresh

CHAPTER 04
Repository and local development workflow
DESIGN PROPOSAL / SEPTEMBER 2026
008
WORKSPACE LAYOUT
apps/mobile: Expo app. apps/web: Next.js buyer and staff routes. apps/api:
NestJS controllers, guards and application services. apps/worker: outbox, retries
and scheduled jobs. packages/contracts: DTO schemas and generated API types.
packages/domain: state transitions and fee calculations. packages/design: tokens
and motion presets. packages/db: schema and SQL migrations.
BOOTSTRAP SEQUENCE
Create a pnpm workspace and commit the lockfile. Scaffold clients and NestJS
using their official generators. Choose a supported Node LTS and mutually
compatible Expo/React Native/Reanimated versions at kickoff; record exact
resolved versions in an architecture decision record. Do not blindly upgrade native
packages independently of the Expo SDK.
LOCAL SERVICES
Use Docker Compose for PostgreSQL/PostGIS and Redis or an isolated local
Supabase setup. Seed fake campuses, students, sellers, inventory and orders.
Supply .env.example with variable names only. Provider adapters use
deterministic sandbox fixtures and signed test webhooks. Never copy production
identity evidence into local development.
DEVELOPER COMMANDS TO ESTABLISH
Define pnpm dev, lint, typecheck, test, test:integration, test:e2e, db:migrate,
db:seed and contracts:generate in workspace scripts. These are required project
conventions, not commands already implemented in the supplied handoff. A fresh
clone must document exact setup and run one seeded buyer-to-hub-to-recipient
journey.

VOSSIE / DEVELOPER GUIDE
CHAPTER 05
Turning the UI atlas into production screens
DESIGN PROPOSAL / SEPTEMBER 2026
009
TRACEABILITY
Preserve A01-U24/B01-X15 IDs in route metadata, tests and design tickets.
Display friendly URLs with resource IDs; do not use a screen code as a substitute
for a resource key. Store screenId, route, component, permissions, query key,
commands and motion IDs in the screen registry.
COMPONENT CONSTRUCTION
Build Button, Field, FormError, BottomSheet, StatusBadge, OrderTimeline,
ScannerPanel, MoneySummary, EvidenceCard and RoleNavigation first. Use
shared colour, typography, radius, spacing and motion tokens. Build forms against
schemas. Responsive staff tables become labelled cards on small screens rather
than squeezed desktop tables.
SERVER STATE AND LOCAL STATE
Use TanStack Query for server resources and invalidation. Keep form drafts and
presentation state local; introduce Zustand only for cross-screen transient state
such as a basket draft. Never keep authoritative money, permissions or custody
solely in a global client store. Clear query caches and secure tokens on identity
change.
REPLACE PROTOTYPE SHORTCUTS
The UI atlas contains buttons such as Preview payment confirmed and cross-role
walkthrough links. Remove those from production. Replace them with
provider/webhook or authorised staff events. The appendix identifies demo
controls. A transition shown in the prototype is a contract to implement, not proof
that a backend already exists.

VOSSIE / DEVELOPER GUIDE
CHAPTER 06
Motion and interactive 3D implementation
DESIGN PROPOSAL / SEPTEMBER 2026
010
SHARED MOTION TOKENS
Proposed tokens: press 120 ms; micro 180 ms; navigation 240 ms; panel 280 ms;
confirmed transition 360 ms; optional celebration 550 ms. Use gentle ease-out
and limited movement. M01-M30 specify exceptions. Cancellation must settle to
the newest valid state, not leave half-visible controls.
NATIVE IMPLEMENTATION
Reanimated handles transform/opacity interactions and follows the system
reduced-motion preference [D2]. Keep input feedback off network timing. Use
stable keys and native-stack navigation. Test gestures with keyboard, screen
reader and scroll interactions. Never animate an entire complex list when a single
row changes.
WEB 3D CHOICE
The supplied parcel is CSS perspective geometry, not a photorealistic model.
Start with this for packaging, a layered icon and an isometric campus illustration. If
a GLB model is approved, lazy-load Three.js within a client-only viewer; fit camera
to container, cap device pixel ratio, dispose textures/materials and render only on
change. Three.js has responsive and on-demand guidance [D3].
PROPOSED PERFORMANCE GATES
Optional viewer target: at most 1 MB compressed asset transfer, one viewer
active at a time, at most 20k triangles for a later model. These are budgets to
validate, not measured results. Target responsive 60 fps on the pilot mid-range
phone, degrade to 30 fps or static when needed. Respect Reduce Motion, in-app
low-motion toggle and reduced-data preference where available. 3D never blocks
ordering.

VOSSIE / DEVELOPER GUIDE
CHAPTER 07
Identity, sessions and student verification
DESIGN PROPOSAL / SEPTEMBER 2026
011
AUTHENTICATION
Use managed Auth for password/email verification and MFA. NestJS verifies JWT
signature against trusted JWKS, algorithm allow-list, issuer, audience and expiry;
do not decode a token and treat claims as proof. Resolve active account and
server-side memberships for protected commands [D4,D5].
SESSION HANDLING
Native refresh credentials use SecureStore rather than unencrypted async
storage [D12]. For web, choose a documented secure cookie/session flow, set
HttpOnly/Secure/SameSite appropriately and protect cookie-authenticated
mutations against CSRF. Rotate and revoke sessions on password changes,
account restriction and staff removal.
VERIFICATION MODEL
Authentication proves account control, not student or government identity. Store
verification requests with status, provider/manual reference, decision actor and
expiry. Buyer student verification precedes marketplace access as required by
policy. Seller/courier identity checks reuse an existing verified identity without
exposing documents to other participants.
MFA AND PASSKEYS
Require step-up MFA for staff sessions, payout destination changes and high-risk
actions. Passkey UI in A10 is capability-gated: enable only after the selected auth
stack supports a tested WebAuthn/passkey flow; otherwise hide it. Staff roles
cannot be self-selected during registration.

VOSSIE / DEVELOPER GUIDE
CHAPTER 08
Permissions, data isolation and staff roles
DESIGN PROPOSAL / SEPTEMBER 2026
012
AUTHORITY MODEL
Use roles plus resource conditions: user owns order, seller owns listing, courier is
currently assigned, hub operator belongs to this hub, incubation staff belongs to
permitted campuses. A user may have several memberships, but each request
uses an explicit permitted context. Deny by default.
DATABASE BOUNDARY
Keep transactional domain tables in a private schema unavailable to public Data
API roles. Apply least-privilege database grants to the API connection. If any
tables/views are exposed via Supabase Data API, explicitly enable and test RLS;
do not assume every creation path enables it [D9]. Service-role credentials never
enter mobile/web bundles.
SEPARATE STAFF CAPABILITIES
Hub intake, hub release, dispatch, moderation, refunds, finance reconciliation,
incubation and platform configuration are independent grants. A generic staff role
is insufficient. Use two-person approval for defined high-risk
grants/refunds/payout overrides; prohibit approving your own action.
INFORMATION BOUNDARIES
Buyers see only assigned courier contact and delivery data for the active order.
Couriers see minimum pickup/drop-off details. Sellers see practical business
feedback, not internal incubation health scores. Signed evidence URLs require
current entitlement. Record attempted denied access without leaking document
content into logs.

VOSSIE / DEVELOPER GUIDE
CHAPTER 09
Database model and migration strategy
DESIGN PROPOSAL / SEPTEMBER 2026
013
CORE RELATIONS
users -> memberships -> campuses/hubs. sellers -> listings -> variants ->
inventory. requests -> offers -> orders -> order_items -> fulfilments -> packages ->
custody_events. service_slots -> slot_holds -> bookings. transfers ->
manifest_items -> scans. payments -> ledger_journals -> ledger_lines ->
payout_allocations. disputes and incubation plans reference their subject records.
REQUIRED COLUMN CONVENTIONS
Use UUID primary keys, created_at/updated_at timestamptz, record_version
integer and explicit status values. Use integer minor units plus ISO currency for
money; never floats. Campus-scoped records carry campus_id with a foreign key.
All external references are uniquely indexed by provider and external ID.
CONSTRAINTS
Unique accepted offer per request; unique active assignment per delivery; unique
package custody transition command ID; no overlapping committed booking for a
seller/resource time range. Reservation counts cannot exceed inventory. Validate
journal balancing inside a transaction or deferred constraint trigger; a row-level
CHECK cannot sum an entire journal.
MIGRATION ROLLOUT
Write reviewed SQL migrations. Use expand/migrate/contract: add nullable field,
deploy compatible code, backfill, validate, then enforce/remove later. Run
migrations once as a release job, not on every API replica start. Test forward
migration on staging and restore from backup before destructive production
changes.

VOSSIE / DEVELOPER GUIDE
CHAPTER 10
Read models, search and geospatial matching
DESIGN PROPOSAL / SEPTEMBER 2026
014
SEARCH BASELINE
Start with PostgreSQL text search and indexed filters for campus, category,
availability and verified publication status. Use cursor pagination with a stable
tie-breaker. Return safe preview fields; never hydrate staff-only seller indicators
into public search results.
LOCATION MODEL
Store approved campus service areas and hub coordinates using PostGIS. Use
spatial indexes for radius checks. Addresses have structured fields plus delivery
notes. Preserve user-picked coordinates with accuracy metadata; a device
location is a suggestion until confirmed by the user.
MATCHING INPUTS
Rank eligible sellers by stock/capacity, category, campus, availability and
policy-defined ranking. Persist the ranking-policy version and relevant snapshot.
Seller listed price remains fixed; ranking is not an auction. Start a small
configurable batch and expand only when no eligible acceptance succeeds.
READ MODELS
Build buyer order summary, seller queue, hub queue and incubation projections
from committed events or SQL views. A projection may lag; commands must
re-check authoritative rows. Return last-updated and record-version fields so
clients can explain stale data.

VOSSIE / DEVELOPER GUIDE
CHAPTER 11
REST commands, API errors and concurrency
DESIGN PROPOSAL / SEPTEMBER 2026
015
CONTRACT FORMAT
Prefix production APIs /v1. Use GET for reads; POST command routes for state
changes; PATCH only for editable drafts/settings. Validate DTOs server-side.
Proposed request headers include Idempotency-Key and If-Match resource
version for protected commands. Do not accept actor_id, price totals or
permissions from client payloads as authority.
SUCCESS AND FAILURE
Return resource ID, state, version and server_time. For queued work, return 202
with command_id and status URL. Errors use code, message, field_errors,
retryable, correlation_id and optionally current_version. Use 401 for
missing/expired auth, 403 or privacy-preserving 404 for denied records, 409 for
state conflict, 422 for validation, 429 for throttling.
IDEMPOTENCY
Persist key scope as actor + route + key with request hash and result. Same
key/same payload returns original result; same key/different payload is rejected.
Clients retry an uncertain command with the same key. Database uniqueness and
provider idempotency remain necessary beyond HTTP middleware.
OPENAPI DISCIPLINE
Define resource schemas and each mutation effect before client implementation.
Generate typed clients and contract tests in CI. The included OpenAPI fragment
shows one acceptance command only; screen appendix APIs are representative
contracts to expand, not a falsely complete API specification.

VOSSIE / DEVELOPER GUIDE
CHAPTER 12
Orders, money and custody are separate states
DESIGN PROPOSAL / SEPTEMBER 2026
016
SEPARATE AGGREGATES
Keep commercial order state, payment state, fulfilment state, package custody
and dispute state separate. An order can be paid with a delivery exception. A
delivered parcel may still have an open dispute. Do not collapse these into one
ambiguous order_status column.
ORDINARY PRODUCT LIFECYCLE
Requested -> seller accepted -> awaiting payment -> paid -> preparing -> seller
drop-off -> hub received -> courier assigned -> collected -> delivered -> buyer
confirmation -> payout eligible. All transitions have guards. Courier dispatch
cannot occur before committed hub receipt for an ordinary product.
FOOD AND SERVICE VARIATION
Food dispatch can start after payment while preparation continues; courier
collects directly from seller. Service flow is slot held -> buyer confirms -> funds
authorised -> seller accepts -> service delivered -> completion review -> release
according to agreed policy. Authorisation is not captured settlement and can
expire.
STATE HISTORY
Each transition writes actor, command ID, from/to state, aggregate version and
evidence references. Return allowed_actions computed from state and
permissions. UI button visibility helps users, but the same guards execute inside
the server transaction.

VOSSIE / DEVELOPER GUIDE
CHAPTER 13
Atomic seller acceptance and reservations
DESIGN PROPOSAL / SEPTEMBER 2026
017
TRANSACTION ORDER
Authenticate seller; validate request campus/category; begin transaction; lock
request, offer and inventory/capacity rows in a consistent order; re-check expiry
and eligibility; reserve quantity/capacity; update accepted seller/order state; expire
competing offers; insert outbox event; commit. PostgreSQL row locks coordinate
concurrent changes [D6].
RACE PREVENTION
Use a unique accepted offer constraint as a backstop. If two accepts race, one
returns success and the other receives 409 with the current state. Retry
deadlocks/serialization failures only with bounded retry and the original
idempotency key. Never hold database locks while calling payment or notification
providers.
TIMEOUT OWNERSHIP
Store expires_at in PostgreSQL. BullMQ triggers checks, but a delayed or missing
job cannot extend eligibility. On acceptance, compare to server time; on
scheduled expiry, re-check state/version before releasing reservations. A
reconciliation sweeper repairs missed expiries.
CONSENT
An alternate seller, changed campus, substitute item or changed quote requires
buyer review. No automatic charge to a changed offer. Keep the accepted quote
snapshot and consent timestamp linked to the order.
IMPLEMENTATION FLOW
Verify actor
Lock + recheck
Reserve stock
Commit + outbox
Return outcome

VOSSIE / DEVELOPER GUIDE
CHAPTER 14
Quotes, variable fees and checkout
DESIGN PROPOSAL / SEPTEMBER 2026
018
QUOTE CONTRACT
Create a server quote with item lines, quantities, unit prices, delivery/transfer fee,
platform fee, discount/subsidy, provider fee treatment, currency, expiry and
fee_policy_version. Store amounts in cents. Include a human-readable
breakdown and a hash/version the buyer accepts.
VERSIONED POLICY
Rules may vary by category, order value, seller/courier standing and delivery
complexity. Store effective_from and effective_to; existing accepted quotes retain
their snapshot. The earlier fixed 2% concept is superseded. Tax treatment and fee
disclosure must be confirmed by the business before production.
CHECKOUT SEQUENCE
For ordinary products, request seller acceptance first, then create the payment
attempt for the accepted quote. Revalidate stock reservation, quote expiry and
delivery eligibility. If anything changes, return a fresh quote and require consent.
Do not silently reprice.
VALIDATION TESTS
Test boundary amounts, rounding allocation, zero subsidies, full discounts,
transfer fees, stale policy versions and concurrent stock depletion. Sum of
displayed line items must equal the authorised amount exactly. No client subtotal
is trusted.

VOSSIE / DEVELOPER GUIDE
CHAPTER 15
Payments and provider adapter
DESIGN PROPOSAL / SEPTEMBER 2026
019
PROVIDER-NEUTRAL INTERFACE
Define createPayment, getPayment, authorise, capture, void, refund,
createPayout and getPayout behind an adapter with an explicit capability matrix.
The research mentions several South African providers; this guide does not claim
any one supports every required flow. Complete a sandbox capability proof before
selection.
WEBHOOK HANDLING
Verify signature using raw request bytes, timestamp/replay rules and configured
secrets. Persist provider + event ID uniquely before processing. Check
order/attempt reference, currency and amount against server records.
Acknowledge only after durable receipt; process idempotently and reconcile with
provider when ordering is ambiguous.
UNKNOWN AND LATE OUTCOMES
A cancelled browser or network timeout is not a failed charge. Return checking
status and query the existing attempt. A late success after reservation expiry
enters reconciliation: restore fulfilment only if still valid and consented, otherwise
initiate an idempotent refund. Never create another charge merely because a
spinner timed out.
LAUNCH GATE
Approve supported authorisation lifetime, partial capture/refunds, marketplace
allocation, payout verification and settlement timing in writing with the selected
provider. Do not implement unapproved custody of client money as a homemade
escrow. Block flows whose required provider capability is absent.

VOSSIE / DEVELOPER GUIDE
CHAPTER 16
Ledger, balances and payout release
DESIGN PROPOSAL / SEPTEMBER 2026
020
ACCOUNTING MODEL
Use immutable double-entry journals with balanced debits/credits per currency.
Separate processor clearing, buyer/customer liability where applicable, seller
payable, courier payable, platform revenue, refunds and payout clearing. An
accountant and provider settlement model must validate final account treatment.
ILLUSTRATIVE POSTING ONLY
A confirmed R100 capture can debit processor receivable and credit an order
allocation liability. On approved allocation, debit that liability and credit
seller/courier/platform accounts according to the fee snapshot. A payout moves
payable to payout clearing, then clears against bank/provider settlement. These
are design examples, not final accounting policy.
ELIGIBILITY VERSUS MONEY
Track payout allocation eligibility separately from ledger ownership. Product
eligibility waits for required completion and dispute rules. Transfers with
discrepancies initially hold affected release; review may release unaffected
package allocations while disputed ones stay held. Reversals create
compensating journals, never edit historic lines.
WALLET SEMANTICS
Spendable, withdrawable and pending are labelled views and may overlap; do not
sum them into a misleading total. R50 minimum withdrawal and up to three
verified destinations are research rules to version. Reserve withdrawable balance
atomically before provider payout; prevent two concurrent withdrawals spending
the same amount.

VOSSIE / DEVELOPER GUIDE
CHAPTER 17
Services, slot holds and authorisation
DESIGN PROPOSAL / SEPTEMBER 2026
021
AVAILABILITY
Store recurring seller availability in local campus timezone and materialise/derive
bookable ranges. Keep appointments as UTC instants with timezone context.
Prevent overlapping bookings for the same resource using range exclusion or a
properly locked slot inventory transaction.
HOLD AND CONFIRM
Propose the next eligible slot, create a server hold for the configured 5-10-minute
window and return expires_at. Buyer explicitly confirms, then provider
authorisation is requested. Commit a booking only according to provider outcome
and seller acceptance. Expired holds cannot be resurrected by a stale client
screen.
DECLINE AND REMATCH
Seller decline triggers buyer-controlled alternatives. Void or reuse authorisation
only if the provider and buyer consent allow the exact flow; do not carry a money
authorisation to a changed service without review. Earlier 30/70 release is a
business proposal requiring policy approval, not a fixed implementation
assumption.
COMPLETION
Seller submits completion evidence, buyer reviews and either confirms or opens a
case. Release is a separate command with state and dispute guards. Scheduled
work must flag authorisations approaching expiry and request explicit recovery
rather than assuming indefinite holds.

VOSSIE / DEVELOPER GUIDE
CHAPTER 18
Hub custody, QR tokens and recipient proof
DESIGN PROPOSAL / SEPTEMBER 2026
022
PACKAGE IDENTITY
Generate a cryptographically random opaque token that maps to a package; do
not encode buyer address, phone, payment or identity data in QR. Treat token
possession as a lookup aid, not authority. Store token hash, expiry/revocation and
permitted use where practical.
CUSTODY COMMAND
Resolve token -> show expected package/current custodian -> collect receiving
condition -> validate actor/hub/assignment -> transactionally append custody
event and update custodian/version. Unique command ID prevents duplicate
confirmation. Store evidence references, timestamp and previous custody event.
HUB REJECTION
Failed intake remains before HUB_RECEIVED. Record rejection reason and
correction deadline, notify seller and block ordinary dispatch. Research proposes
24 hours for correction; the scheduled expiry cancels the eligible order and
initiates the appropriate refund/release workflow, reconciled to provider outcome.
RECIPIENT HANDOVER
Generate a single-use PIN for this handover; store a slow hash or keyed verifier
and enforce attempt limits. Verify only after correct order and delivery actor are
resolved. Never log PINs. GPS proximity can help detection but cannot substitute
for recipient proof. Camera APIs support barcode scanning; permissions and
lifecycle require handling [D10].
IMPLEMENTATION FLOW
Resolve token
Check authority
Record condition
Commit custody
Update UI

VOSSIE / DEVELOPER GUIDE
CHAPTER 19
Courier dispatch and location pipeline
DESIGN PROPOSAL / SEPTEMBER 2026
023
DISPATCH ELIGIBILITY
Query approved courier, transport mode, campus coverage, capacity and current
assignments. Ordinary product dispatch requires hub receipt. Food allows
dispatch after payment with direct seller pickup. Offer acceptance locks
delivery/assignment and uses unique active assignment protection.
LOCATION INGESTION
Accept sequence, timestamp, latitude, longitude and accuracy only from the
assigned active courier. Rate-limit, validate ranges, reject stale/out-of-order
samples and detect implausible jumps for review. Store latest location separately
from custody. Retain detailed traces only under an approved retention policy.
CLIENT DELIVERY
Authorise each order subscription. Send minimal location updates with version
and sample age. Client interpolates between known samples, stops following after
map panning and displays stale status. A reconnect fetches the latest snapshot.
Expo background location requires platform permissions/configuration and can be
interrupted by OS lifecycle [D11].
MAPS ADAPTER
Use a maps/geocoding/routing provider chosen after South African coverage and
cost testing. Restrict client keys by app/domain; keep server routing secrets
private. Build address lookup, route estimate and reverse-geocode interfaces.
ETA is an estimate with last-update time, never a guaranteed promise.

VOSSIE / DEVELOPER GUIDE
CHAPTER 20
Food and failed-delivery recovery
DESIGN PROPOSAL / SEPTEMBER 2026
024
FOOD WAITING
After payment, dispatch may proceed while food prepares. Courier waits within
the configured 10-15-minute policy before eligible release/rematch. A timer job
re-checks current state and does not blindly cancel an already-collected order.
Food does not inherit ordinary hub storage rules.
BUYER UNAVAILABLE
Courier records arrival and attempt according to policy, waits 10-15 minutes, then
requests return. Ordinary parcel return is a new custody transition to hub, not an
automatic marker reversal. The hub records condition and starts the configured
48-hour collection window.
ESCALATION
On uncollected expiry, open seller recollection and any approved handling-fee
workflow. Food/perishables require their own approved disposition/refund rules.
Damage, unsafe conditions and recipient mismatches open support cases. Never
tell a courier to leave goods unattended without a specifically authorised policy.
TEST TRANSITIONS
Cover buyer returns during timeout, courier loses signal, seller finishes food just
as courier releases, hub rejects returned package, duplicate timeout jobs and
payment refund pending. Every timer has a database deadline,
cancellation/version guard and recovery route.

VOSSIE / DEVELOPER GUIDE
CHAPTER 21
Cross-campus transfers and manifests
DESIGN PROPOSAL / SEPTEMBER 2026
025
PLANNING
Maintain three configurable daily transfer windows per participating route. Prefer
approved institutional transport; student overflow requires opt-in and eligible
vehicle mode. Do not assign bulk transfer to a walking/bicycle courier where policy
forbids it.
MANIFEST LOCK
Build a draft manifest with exact package IDs, source/destination hubs and
assigned transport. Lock before dispatch. Origin scans must reconcile the exact
expected set. After locking, edits require an explicit versioned amendment and
revalidation; no silent additions.
DESTINATION
Record arrival; scan the same package set and receiving conditions. Missing,
unexpected or damaged packages create an exception with evidence. Equal
counts alone are insufficient. Publish delivery-to-local-hub readiness only for
packages actually received.
ALLOCATION RELEASE
A discrepancy triggers the defined payout hold. Review can isolate disputed
package allocations and release unaffected allocations with an audit trail. Route
staff do not directly mutate wallet balances; they submit evidence to the eligible
release process.

CHAPTER 22
Uploads, messaging and notifications
DESIGN PROPOSAL / SEPTEMBER 2026
026
MEDIA PIPELINE
Issue short-lived signed upload URLs after permission and quota checks. Write
into a quarantine bucket; inspect content type, size and malware; strip
unnecessary metadata; generate safe thumbnails; promote only approved public
listing media. Identity and dispute evidence remain private with retention and
deletion rules.
MESSAGING
Create conversations scoped to order/booking/support participation. Persist
message and outbox event in one transaction. Use client_message_id for
deduplication. Attachments share the safe upload pipeline. Delivered and read
receipts are separate optional events with clear semantics.
PUSH AND EMAIL
Outbox workers enqueue push/email according to user preferences and
transactional necessity. Push payloads contain minimal identifiers, not private
evidence or PINs. Deep links authenticate then re-check access. Rotate invalid
push tokens and record delivery outcome without treating push delivery as user
acknowledgement.
ABUSE CONTROLS
Rate-limit messages/uploads, allow reporting/blocking subject to order support
obligations, moderate public material and log provider failures. A client cannot
send an arbitrary push to another user ID. Calls need a separate approved
masked-calling integration; the prototype call button is not an implemented
telephony service.

READ-SIDE EVIDENCE

CHAPTER 24
Disputes, moderation and audit
DESIGN PROPOSAL / SEPTEMBER 2026
028
CASE LIFECYCLE
Open -> triaged -> evidence requested -> under review -> decision proposed ->
approved/executed -> appeal/closed. Model commercial and safety severity
separately. Freeze only allocations or privileges justified by case policy. Return
understandable participant status without disclosing another party's private
evidence.
DECISION EXECUTION
A moderation decision records reason, policy version, evidence IDs, actor and
affected resources. Financial outcomes call payment/ledger commands; they
cannot update a balance directly. High-risk decisions require a second approver
and recent MFA.
AUDIT INTEGRITY
Append audit records with correlation ID, actor membership, action, subject,

deletion and export. Consider tamper-evident storage for required audit trails once
retention and assurance needs are agreed.

Participant appeal O08 uses a user-facing view, not the staff queue. Revoking
staff access terminates subscriptions/sessions and invalidates cached protected
data. Deletion requests track workflow and any approved retention obligations
rather than instantly deleting ledger history.

VOSSIE / DEVELOPER GUIDE
CHAPTER 25
Realtime, outbox and background jobs
DESIGN PROPOSAL / SEPTEMBER 2026
029
OUTBOX TRANSACTION
Every protected mutation inserts domain changes and outbox record in one
PostgreSQL transaction. Worker claims records safely, publishes with event_id
and retries on failure. Consumers maintain dedupe records. Do not promise
exactly-once network delivery; design at-least-once delivery with idempotent
effects.
EVENT ENVELOPE
Include event_id, type, schema_version, aggregate_id, aggregate_version,
occurred_at and minimal permitted payload. Clients reject older versions; gaps
trigger a fresh snapshot. Access-check each subscription and re-check on role
revocation or assignment change.
JOBS
Use deterministic job identity for reminders, expiries, refunds, reconciliation and
notification attempts. BullMQ recommends retry-safe idempotent job design [D7].
A worker crash after provider success must reconcile before repeating a payout or
refund.
OPERATIONS
Track queue age, failed attempts and dead-letter items. Use exponential backoff
with jitter and provider rate limits. Staff replay tools display original
command/effect and require authorisation. A database sweeper finds expired
holds and unsent outbox rows after Redis outages.

VOSSIE / DEVELOPER GUIDE
CHAPTER 26
Offline behaviour and recovery
DESIGN PROPOSAL / SEPTEMBER 2026
030
ALLOWED OFFLINE
Permit reading labelled cached catalogues and owned order summaries, safe
local draft editing and non-binding basket changes. Show cache timestamp and
network state. Minimise cached personal data; clear on logout and account
switch.
BLOCKED OFFLINE
Do not finalise payment, accept seller/courier offers, validate recipient PINs,
confirm custody, approve refunds or grant staff access offline. A captured scan
can be shown as unverified pending input, never completed custody. High-risk
commands require fresh state after reconnect.
RECONNECT PROTOCOL
Refresh session, re-check membership, fetch relevant snapshot, compare
resource version, reconcile uncertain command by idempotency key, then allow
another action. Do not replay an entire offline queue of irreversible commands
automatically.
CONFLICT UX
If price, availability, recipient, assignment or policy changed, show old/new values
and require review. Preserve safe form values. Return to the named recovery
screen in the atlas. Reduced motion and offline mode are independent settings.
