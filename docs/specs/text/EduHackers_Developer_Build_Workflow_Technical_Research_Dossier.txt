1. Executive summary
This dossier continues the earlier EduHackers marketplace research, but shifts the lens to the developer, build workflow and
technical architecture. The question is not only what the product should do. It is how the system should work, how different
parts should communicate, what should be built first, what should be researched further, and how the team should manage
engineering work from GitHub to prototype testing.
The central technical hypothesis is that EduHackers should adapt on-demand marketplace patterns, especially dispatch, live
status and dynamic fulfilment, without simply copying Uber, Uber Eats or Mr D. Those platforms already prove the value of
real-time matching, courier tracking, busy modes, live order states and dynamic supply-demand balancing. EduHackers
differs because it must combine buyer demand, student sellers, campus hubs, QR custody, hub-to-hub transfers, student
couriers, staff operations, marketplace payment logic and Incubation Hub intelligence inside a closed Eduvos environment.
The recommended research architecture is one EduHackers platform with two application families: a student-facing
Marketplace and a role-based Operations Platform. Both should share one identity system, one backend domain model, one
API contract set and one event model, while still providing very different user experiences for buyers, sellers, couriers, hub
operators, transport staff, moderators, admins, finance operations and Incubation Hub staff.
The hardest proof is not visual polish. The hardest proof is state correctness: only one seller can win a request, only one
courier can take a delivery, a service slot cannot be double-booked, a package must have a reliable custody chain, a
payment/ledger split must be auditable, and every real-time screen must recover correctly when connectivity drops. The
Proof of Flow should demonstrate those system behaviours before the team attempts the full super-app.

2. Research scope and decision discipline
This document is research. It records the current best hypotheses based on team discussion, existing platform patterns and
available technical documentation. It is not yet a final build specification. The purpose is to give the developer, product lead,
UX/UI designer, business analyst and pitch lead a shared map of what needs to be tested, what should be built in a POF,
and what requires Eduvos, payment-provider or legal confirmation.
The research method used in this dossier is comparative and system-oriented. For each major feature, the report asks what
already exists in similar platforms, what EduHackers can learn from it, where the existing pattern does not fit Eduvos, what
EduHackers should research as its own hypothesis, and what evidence would prove or disprove that approach.
The repeated rule is: do not turn a brainstormed idea into a final requirement until it survives a technical feasibility check and
a user/operations validation check. Where the team has selected a direction, this report marks it as a working hypothesis
unless the decision depends purely on internal project preference.

3. Product system overview
The strongest architecture is not one application with everything hidden in menu tabs. EduHackers should be researched as
a platform with two application families. The Marketplace is used by students as buyers, sellers and couriers. The Operations
Platform is used by Hub Operators, Transport Operators, Incubation Hub staff, moderators, finance operations and admins.
These apps share the same backend services but expose different workflows, data, security controls and dashboards.
This separation matters because the Marketplace must feel quick and student-friendly, while Operations must be reliable,
auditable and role-specific. A Hub Operator needs scan queues and custody states, not a shopping feed. Incubation staff
need demand intelligence and business health indicators, not courier live-trip controls. Admins need policy configuration, not
buyer checkout screens.

4. Uber-style dispatch model, adapted
The team asked whether EduHackers can work like Uber: a client requests something, matching participants receive live
offers, the first suitable participant accepts, and the system locks the job. The research answer is yes, but the match target is
not only a driver. EduHackers must match buyers to sellers, sellers to hubs, hubs to couriers, transfer batches to transport
capacity and service buyers to available seller slots.
The platform should not be a bidding marketplace. Sellers list fixed prices. Buyers request a listed product or service. The
backend uses the listing price snapshot and availability at the time of request. No counter-offers or buyer proposed budgets
are involved in the Uber-style flow.
Seller matching hypothesis
When a buyer requests a listed item or service, the system ranks eligible sellers by campus, category, stock or availability,
trust standing, capacity, response reliability and fulfilment suitability. Instead of notifying one seller at a time, the current
research direction is small staggered batches. Batch 1 may notify a few best-fit sellers over 30 to 60 second intervals. If no
one accepts, the next batch expands. If local supply fails, the system expands to the next viable campus.
Once any seller accepts, the backend immediately locks the order to that seller and cancels all other open offers. This
acceptance must be atomic. If several sellers tap accept at the same time, one backend transaction must win and every
other response must receive a "request already accepted" result.

5. Seller dispatch state model
The state model needs to be explicit because dispatch bugs become trust bugs. The buyer should not see multiple sellers
accepting the same request. Sellers should not prepare orders that were already won by someone else. Stock should not be
oversold. Service slots should not be double-booked. The backend must own these transitions.

6. Seller capacity and Busy Mode research
Existing merchant platforms show that high order load needs operational controls. DoorDash allows merchants to slow or
pause orders through its status controls, and Uber Eats provides Busy Mode, preparation-time tools and pause capabilities
for stores that are overloaded. These patterns support the EduHackers hypothesis that student sellers need workload
controls rather than being expected to accept every request indefinitely. [R5] [R6]
The EduHackers version is adapted to student sellers. Instead of only adding prep time, the platform should enforce a
maximum number of simultaneous accepted orders per category and an overall account cap. The team selected 15
maximum active orders per category and 25 maximum active orders overall as research hypotheses. These caps protect
students from overload and protect buyers from delays.

cannot override the system maximum upward.

7. Product fulfilment: campus hub model
For normal physical products, the preferred research model is not seller-to-courier direct handoff. The seller drops the
packaged item at a designated campus hub. The hub scans the package, records condition and accepts custody. Only after
the package is physically confirmed at the hub does courier dispatch begin. This prevents couriers from travelling to collect
products that are not actually ready.
This hub-and-spoke model is a major EduHackers differentiation. Standard delivery apps often connect courier directly to
merchant. EduHackers researches a campus custody layer, which can improve scheduling, traceability, privacy and safety in
a closed university environment.

8. Package QR, PIN and custody model
The chain of custody should use two different proof types. The package QR proves that the physical package is the correct
package. The buyer PIN proves that the authorised buyer or recipient received it. The QR should contain only an opaque
token. It must not expose buyer address, payment details, phone number or identity data.
At every custody transfer, the receiving party records package condition. The official condition baseline starts when the Hub
Operator receives the package, not with seller photos. If a package is poorly packaged, unsealed, leaking, visibly damaged
or unsuitable for transport, the hub can reject it before custody is accepted.
 Figure 5. QR and PIN serve different proof functions. QR confirms the object; PIN confirms the recipient.
Package rejection and correction
If hub intake rejects a package, the seller receives a 24-hour grace period to fix and return it. The buyer, seller and relevant
logistics participants are notified of what is happening. If the seller does not return an acceptable package within 24 hours,
the order is cancelled, buyer payment is refunded/released and the missed correction deadline is recorded against seller
reliability.
Repeated packaging issues should trigger Eduvos-approved learning resources, but training completion must remain
educational only. It should not give reliability points or automatically restore standing. Marketplace reliability should be driven
by marketplace behaviour, not whether a resource was completed.

9. Food and perishable fulfilment
Food should not be forced through the hub flow. The team correctly identified that prepared meals and perishable goods may
degrade or create safety issues if held at a pickup hub. For food, the courier workflow should begin immediately after seller
acceptance and payment confirmation, while the seller is still preparing the food. The courier travels toward the seller so
pickup can happen as soon as the food is ready.
Uber Eats documentation emphasises preparation-time accuracy, Busy Mode and ready-for-pickup behaviour to reduce
courier wait time. EduHackers can learn from this while adapting the model to student sellers, campus geography and
category-specific food compliance. [R6] [R7]

10. Courier platform model
All courier workflows should share one courier platform capability set. Live tracking, ETA, in-app messaging, masked or
in-app calling, one-time PIN confirmation, earnings records, reliability events and payout logic should be core courier
infrastructure. Food, normal products and transfer routes differ in pickup strategy, not in basic courier capability.

Courier reliability
If a courier accepts a job and then does not move toward the hub for a configurable period, the system should warn them first
and then release the job back into matching if there is still no progress. Repeated accept-then-cancel, missed pickup
deadlines or unexplained inactivity should reduce future matching priority and can eventually cause a temporary delivery
pause. The architecture must distinguish GPS/connectivity problems, campus access issues, buyer delays and courier
behaviour.

11. Same-campus delivery and failed handoff
For normal product delivery, the courier receives the package from the campus hub, not directly from the seller. If the courier
reaches the buyer and the buyer is unavailable, the courier waits 10 to 15 minutes while the buyer and courier can
communicate via app chat/call. After that, the package returns to the designated campus hub rather than to the seller directly.

12. Hub-to-hub transfer model
For cross-campus fulfilment, the research direction is hub-to-hub transfer rather than direct long-distance courier delivery to
each buyer. The package moves from seller campus hub to destination campus hub through scheduled transfer windows,
then the buyer can collect or use local last-mile delivery.
The team selected three scheduled transfer windows per day as a research hypothesis. Eduvos-approved transport should
be prioritised as the scheduled backbone, with verified student transfer couriers available for overflow. If Eduvos-approved
capacity is full, the buyer can either wait for the next standard window or request an earlier student-courier overflow transfer
and pay the extra charge only if a courier accepts.

13. Transfer exceptions and custody evidence
If a destination Hub Operator finds that a package is missing, damaged, tampered with or does not match the manifest, the
whole transfer payout should initially be held. After the affected packages are identified, unaffected packages can be
completed and the related portion of courier earnings released. Only the disputed portion remains held while the investigation
continues.
The system should not assume courier fault. The purpose of QR scans, custody events and condition checks is to
reconstruct where an issue likely occurred. Every physical handoff should produce a condition record: sealed/intact,
damaged, opened/tampered, packaging compromised or other exception. Exceptions should require photos and notes.

14. Services and appointment booking
Services should not behave like products. The research model uses broad service availability windows plus bookable slots
inside those windows. Buyers do not manually browse a calendar by default. Instead, the system proposes the next available
suitable slot, then asks the buyer to confirm it before booking is final.
The proposed service slot is temporarily held for 5 to 10 minutes, dynamically adjusted by service type, urgency and scarcity.
While held, the slot is unavailable to other buyers. If the buyer rejects the proposed slot, the system proposes another slot
rather than forcing them into a complex calendar.

15. Payment, wallet and ledger research
Payment is one of the highest-risk technical areas. EduHackers should not literally hold money itself unless a regulated
arrangement permits it. The safer research architecture is that EduHackers stores transaction states and ledger entries while
a payment provider remains the system of record for authorisation, capture, refund, split settlement and payout where
applicable.
Paystack supports transaction split APIs that let merchants split settlements across payout accounts and subaccounts, which
makes it relevant prior art for marketplace research in South Africa. [R13] The architecture should remain provider-agnostic
because Ozow, Payfast, Paystack, bank EFT and future wallet partners may differ in authorisation, refunds, incremental
payments, splits and payout capability.

Credit and withdrawals
EduHackers credit can be used across the ecosystem: products, services, delivery fees, transfers, rentals, tickets and other
approved charges. The team selected withdrawable credit with a R50 minimum withdrawal. This requires careful research
because withdrawable stored value looks materially different from a simple non-cash coupon. The safer approach is to
integrate a suitable payment/wallet partner rather than making EduHackers the regulated store-of-value operator.
Users may save up to three verified payout destinations. Adding or changing a payout destination requires step-up
verification. Once verified, it can be used for instant withdrawal immediately, with suspicious withdrawals retained as an
exception-path security review rather than part of normal UX.

16. Fees and dynamic pricing research
The team selected a variable fee model rather than one fixed fee for everyone. Fees can vary by category, order value,
transaction type, Trusted Seller/Courier status, delivery complexity and subsidy rules. The platform can take fees from both
seller transactions and courier delivery fees because it carries matching, payment, operations, infrastructure and support
costs.
Existing on-demand platforms use dynamic supply-demand mechanisms, but EduHackers should avoid opaque surge-style
pricing. Uber describes surge as a real-time response to demand/driver imbalance, while telling riders the higher price before
commitment. [R4] EduHackers should research a more bounded and transparent approach: seller prices remain fixed by
sellers, while delivery/transfer incentives can adjust within admin-defined caps based on distance, urgency, courier supply
and campus route capacity.

17. Identity, verification and roles
EduHackers should use one identity system for both Marketplace and Operations. A user starts as an Eduvos-verified buyer.
Government ID verification is required only when activating Seller or Courier mode. If a student verified ID for Seller mode
and later activates Courier mode, the ID verification is reused; only courier-specific checks are added.
For recurring login, the research should consider passkeys and device biometrics rather than building a custom
facial-recognition database. FIDO passkeys use device biometric/PIN unlock while the server verifies cryptographic proof,
which reduces biometric data risk. [R18] Actual facial identity verification should remain a separate, higher-risk research
branch.

EduHackers requires a real-time layer because seller offers, courier offers, live tracking, chat, hub scans, transfer progress
and service slot timers cannot depend only on page refreshes. However, WebSockets should not become the source of truth.
The database and REST API remain authoritative; WebSockets distribute live state changes to connected clients.

32. Differentiation summary
Existing platforms already demonstrate many individual pieces: dynamic dispatch, food-delivery live tracking, merchant busy
mode, order pauses, marketplace splits, GitHub CI/CD, passkeys, spatial databases and real-time communication.
EduHackers should not pitch these individual components as if they are new.
The stronger differentiation is the system combination: verified Eduvos identities, student sellers, campus hubs, QR/PIN
custody, category-aware fulfilment, hub-to-hub transfer windows, student courier earnings, staff operations, protected ledger
states, demand intelligence and Incubation Hub intervention. This is a campus entrepreneurship operating system, not just
an Uber clone or a listing app.
The technical research therefore recommends building a POF that proves the closed operational loop: demand is created, a
seller is matched, the package is protected through custody events, a courier fulfils the delivery, payments are traceable,
Operations can see exceptions, and system data can feed future marketplace and Incubation decisions.

The platform will use countdowns, live maps, urgent requests and operational dashboards. Accessibility cannot be left to final
styling. Low-vision users, keyboard users and screen-reader users need readable status, not color-only signals. Performance
also matters because students may use ordinary mobile data and older phones.
Constraint
Research response
Urgent notifications
Provide text, vibration/sound where permitted, and screen-reader-friendly labels
Color-coded status
Never rely on color alone; include text status and icons/labels
Countdowns
Server-based times with accessible announcements at key thresholds
Maps
Offer text status and ETA fallback when map interaction is not usable
Large dashboards
Use filtering, role-based home views and exportable detail
Low bandwidth
Core order/dispatch screens must work without heavy media
Motion graphics
Use restraint and respect reduced-motion settings
Accessibility should be measured with keyboard navigation, screen reader checks and contrast testing during the
design/build cycle, not after the pitch deck is finished.

47. Final developer research position
EduHackers can research and build an Uber-inspired marketplace dispatch system, but the opportunity is not to copy Uber.
The opportunity is to build a campus-specific commerce and operations system where dispatch, custody, student delivery,
protected payments and Incubation intelligence work together.
The current best direction is a hybrid service-oriented platform with a student Marketplace app family and a role-based
Operations Platform. PostgreSQL/PostGIS, TypeScript, Next.js, React Native/Expo, Tauri, NestJS, Redis/BullMQ and
GitHub Actions are a sensible research baseline, but every provider decision remains open until the team validates cost,
team skill, Eduvos constraints and POF feasibility.
The next immediate action is to convert this research into a team walkthrough, then define the POF backlog in GitHub. The
POF should prove the state machines and trust mechanisms first. After that, UI polish, broader marketplace modes and
advanced features become much safer to build.
