Figma MCP operating loop
1. ChatGPT maintains screen architecture, interaction rules, naming and acceptance criteria. 2. Figma MCP reads
the existing library and, where the account permits write access, creates or updates native frames, components,
variables and Auto Layout. 3. Designs are reviewed in Figma. 4. Cursor receives Figma context and implements the
corresponding React components. 5. VS Code is the independent verification environment. 6. Differences return to
Figma/specification or code as an explicit correction rather than silent drift.
Responsive rule
The same product behaviour is expressed differently by available space: phone uses mobile-first navigation and
sheets; tablet uses split/contextual views; desktop uses sidebars, multi-column layouts, larger maps and operational
tables. Responsive variants share semantics, tokens and component contracts.
Account/cost constraint
Figma's remote MCP can provide design context broadly, but write-to-canvas availability depends on Figma
seat/plan conditions and is currently beta. Therefore automated Figma writing is an accelerator, not a requirement
for Vossie to function. If write access is unavailable, the same design specification and components remain usable
manually and by code-generation workflows.

Decision 02 - Vossie motion & microinteraction system
Motion must communicate hierarchy, state and causality without turning Vossie into a visually noisy interface. The
core application animation layer is Motion.dev/CSS. Motion.dev's free AI Kit skill and documentation search can be
connected to Cursor; premium Motion+ capabilities are optional and must not be required.

Reusable motion tokens
Enter / Exit / Tab Shift / Sheet Up / Card Lift / Expand / Collapse / Progress / Map Pulse / Success / Stagger /
Counter / Reduced Motion. Each token gets approved duration/easing/physics and is reused across roles. Screen
designers choose from the vocabulary instead of inventing new animation behaviour.
Implementation pipeline
Figma state/interaction -> motion specification -> Motion.dev/CSS implementation in Cursor -> browser
preview -> VS Code/Playwright verification -> accessibility/performance check -> reusable component
approved. Motion.dev's free agent skill and current-documentation MCP search support the implementation.
Premium examples, MotionScore and advanced editor features remain optional.
Accessibility and performance gates
Respect prefers-reduced-motion. Never make animation the only carrier of meaning. Prefer transform/opacity for
routine movement, avoid unnecessary layout-triggering animation, keep input feedback fast, and do not block
navigation or transaction completion on decorative motion. Repeated animations must remain calm enough for
sustained marketplace use.

Decision 03 - Motion.so generative motion layer
Motion.so (Mosaic Motion) is separate from Motion.dev. It is an AI motion-video system with an MCP/API workflow.
It can generate motion videos from prompts and can accept design guidance and reference assets. This is useful for
showpiece assets, but its API/MCP jobs consume credits, so it is not a core prototype dependency.
Appropriate uses
Vossie logo/identity animation; short onboarding or feature explainers; presentation/showcase sequences; launch
visuals; optional animated assets that can be exported and embedded without requiring Motion.so at runtime.
Do not use it for
Login-field feedback, navigation, loading indicators, cards, checkout state, courier interaction, operational
dashboards or any other functional UI behaviour. Those remain native application interactions using
CSS/Motion.dev.
Zero-budget rule
R0 core dependency budget: no paid service is required for the prototype to operate. Motion.so output may be
used only when free/sponsored credits are available or when an asset has already been generated and exported.
Loss of Motion.so access must not break a Vossie flow.
