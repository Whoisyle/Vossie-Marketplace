1. Executive summary
Vossie has evolved from a campus buy-and-sell concept into a closed student commerce, logistics and
entrepreneurship platform. The core architecture is one platform with two application families sharing identity,
permissions, orders, payments, custody, realtime events, analytics and audit infrastructure.
Core thesis: Vossie's differentiation is not merely 'a marketplace for students'. The
stronger proposition is verified campus identity + multi-role student participation +
campus logistics/custody + cross-campus transfers + operational tooling + demand
intelligence for student entrepreneurship.
The student-facing Vossie Marketplace combines Buyer, Seller and Courier modes under one verified student
identity. Vossie Operations serves hub staff, transfer operations, Incubation, support, moderation, finance,
compliance, security and administrators through separate permission-controlled workspaces.
The existing engineering package is extensive but is not a finished application: it specifies 90 database tables, 202
API operations, 177 screens, 514 action bindings and 385 delivery tickets. A restricted backend foundation exists,
while most screens, handlers, provider integrations and production deployment remain implementation work.

3. Identity, authentication and security
The preferred long-term model is institutional federation rather than Vossie reproducing the institution's
authentication stack. Where Eduvos identity is backed by Microsoft/Entra, the intended flow is Vossie -> institutional
sign-in -> institutional MFA/Authenticator -> verified identity result -> Vossie session. Vossie should never receive or
store the student's Authenticator secret.

For a zero-budget prototype, this must be an explicitly labelled sandbox simulation: student number / institutional
identity -> simulated Authenticator approval -> verified student state -> campus association -> Vossie account.
Student-card information can support verification or campus interactions, but a photographed card should not

Production authorisation must be enforced server-side. A hidden UI button is not access control. Sensitive

4. Payments and transaction security
Vossie should orchestrate commerce without storing raw card numbers, CVVs or authentication secrets. A
regulated payment provider should handle payment credentials. Vossie stores transaction references, status,
amounts, fees, allocations, refunds and payout state.
The money model should use auditable ledger journals/lines rather than repeatedly mutating a single balance.
Payment callbacks must be idempotent, and order state, money state and custody state must remain distinct.
Prototype payment journey: Checkout -> provider/sandbox authorisation -> Payment
secured -> Seller preparing -> Fulfilment/custody -> Buyer receipt confirmation ->
Transaction completed -> Seller/courier payout eligibility. Refund and dispute paths
must also be demonstrable.
5. Cross-campus commerce and custody
Cross-campus operation is one of the strongest differences between Vossie and a conventional classifieds
experience. A buyer at one campus can discover an item at another campus and choose an authorised fulfilment
path: collection, eligible courier delivery, or hub-to-hub transfer.
A robust transfer path records Seller -> Origin Hub -> QR custody event -> Manifest/Transfer -> Destination Hub ->
QR custody event -> Buyer -> recipient QR/PIN confirmation. Each handoff produces evidence for tracking,
exceptions and disputes. Offline clients must not falsely confirm authoritative financial or custody events.
6. Incubation intelligence
Incubation is not the seller's ordinary dashboard. Seller Mode provides the seller's own listings, orders, inventory,
earnings and analytics. Incubation receives appropriately scoped aggregate intelligence about demand, unmet
searches, stock-outs, category trends, business health and intervention opportunities.
This creates a feedback loop unavailable in a simple listings app: marketplace behaviour can reveal unmet campus
demand; the Incubation team can use those signals to support student businesses; new supply can then return to
the marketplace.

What the research changes
Student-only access by itself is not unique. Current apps already market verified/campus-restricted student
marketplaces. Likewise, chat, listings, search, ratings, protected payments and courier integrations are established
marketplace features. Vossie should not present those as its primary moat.

handoffs; cross-campus manifests and transfers; an institution-facing Operations console; and Incubation
intelligence generated from marketplace demand.
Positioning recommendation: do not pitch Vossie as 'Facebook Marketplace for
students'. Pitch it as a verified campus commerce network that connects student
demand, student businesses, student delivery, campus logistics and entrepreneurship
support in one operational system.

9. Visual and interaction direction
The existing Vossie visual system uses warm ivory #FAF8F2, navy #29475B, powder blue #AFCBDE, slate
#567487 and pale sage #DDE5D9. The intended visual literacy is soft and restrained, while interaction patterns
borrow the clarity and immediacy of on-demand apps: strong cards, obvious states, one primary task per screen,
live status and recovery paths.
The design must remain accessible: persistent labels, visible focus, practical touch targets, reduced-motion
alternatives, clear loading/empty/error/offline states and explicit confirmation for irreversible actions.

14. Pilot Policy Defaults & Money Model
Working decisions from the pre-build research session. These are product rules to validate during the pilot, not final
financial or regulatory assumptions.
14.1 Revenue model selected
Vossie uses transaction-based percentage revenue. A percentage is deducted from the seller's transaction
earnings, and a percentage is deducted from the courier's delivery earnings. Under the current working model, the
buyer is not charged a separate Vossie percentage fee.
The exact seller and courier percentages remain undecided. They should be set only after payment-provider costs,
tax/accounting treatment, courier economics and pilot affordability are researched.

Courier earnings mirror the seller model: Pending when a delivery is accepted, Secured when the delivery allocation

The product should distinguish Pending, Secured, Available and Paid Out instead of displaying one ambiguous
wallet balance. Internally, order state, payment state, custody state and payout state remain separate. Vossie's
platform revenue, seller allocation, courier allocation, refunds and reversals should be represented as auditable
ledger entries.

16. Authentication Research & Prototype Workflow
Core security principle: an identifier format is not proof of identity. An EDUV-style student number or an address
ending in an institutional domain can be useful validation data, but access must not be granted merely because a user
can type a correctly formatted value.
Production target
The target architecture is institutional federation: Vossie -> Continue with Eduvos -> Eduvos/Microsoft identity
provider -> existing Microsoft Authenticator/MFA -> signed authentication response -> Vossie validates
trusted issuer/tenant/token -> active-student eligibility check -> Vossie session. Eduvos/Microsoft remains
responsible for the student's institutional password and MFA. Vossie does not store or receive the student's password,
Authenticator seed or approval code.
Authentication, eligibility and authorization remain separate. Authentication establishes control of the institutional
account. Eligibility establishes that the person is currently permitted to participate as an Eduvos student. Authorization
determines Buyer/Seller/Courier capabilities inside Vossie.
One identity, progressive roles
There are no separate Buyer, Seller and Courier login systems. A verified Vossie student identity receives Buyer
access as the base marketplace capability. Seller and Courier are activated after login through additional role-specific
onboarding, agreements, payout information and approval. One student can therefore hold Buyer + Seller + Courier
capabilities simultaneously.

18. Payment Gateway & Financial Security Workflow
The payment architecture separates marketplace entitlement from movement of regulated funds. Vossie maintains the
authoritative internal ledger for allocations and eligibility; the payment service provider (PSP) remains authoritative for
payment execution, refunds and payouts. Vossie must not present itself as independently holding escrow funds unless
the eventual regulated commercial arrangement explicitly permits that structure.
Confirmed transaction workflow
Stage
System behaviour
1. Checkout
Buyer enters payment through PSP-hosted/tokenised payment infrastructure. Vossie does not store raw
card number or CVV.
2. Provider confirmation
PSP confirms server-to-server. Vossie verifies webhook authenticity, order reference, amount/currency
and processes the event idempotently.
3. Ledger
Append-only journal records buyer payment, seller allocation, courier/logistics allocation where applicable,
Vossie commission and processor cost as distinct components.
4. Secured earnings
Seller entitlement becomes Secured, not yet payout-eligible. Client UI cannot declare payment success.
5. Delivery
QR custody and final OTP evidence drive fulfilment state. OTP proves delivery, not product satisfaction.
6. Protection
Delivered order enters the confirmed 24-hour Vossie Purchase Protection issue window. A qualifying
dispute freezes the affected seller allocation.
7. Available
No qualifying issue / resolved release -> seller entitlement becomes Available.
8. Payout
Automatic or manual payout is requested through the PSP to a verified payout destination; provider result
moves state through Payout Processing -> Paid Out.

Provider strategy
Prototype direction: use a PSP sandbox through a provider-neutral PaymentProvider adapter and simulate the full

Financial state vocabulary

components. Refunds create reversing/adjusting entries rather than deleting or rewriting historical journals.

Confirmed Direction
Food remains available through the normal Seller capability; Vossie does not create a separate seller account merely
because a student lists food. Food does, however, invoke a stronger category-specific workflow for applicable

responsibilities, but the platform must not imply that consumer or food-law obligations have been waived.

Seller obligations
Food-specific Seller Terms should require truthful product information; accurate ingredient/allergen disclosure to the
extent applicable; compliance with applicable food laws; appropriate preparation, storage and transport; truthful
dietary/safety claims; cooperation with incident investigations; and prompt disclosure of known contamination or safety
concerns. These are marketplace obligations in addition to applicable law, not substitutes for it.
Prepared-food inventory & traceability
Prepared food should be batch/time-aware rather than persistent ordinary stock. A preparation batch records seller,
listing, quantity, preparation/availability timestamps, affected orders and fulfilment events. Remaining prepared-food
availability is removed at the appropriate cutoff instead of carrying stale inventory into the next day.

Fulfilment constraint
Prepared meals should begin as same-campus/local pickup or local courier fulfilment, not the ordinary inter-campus
parcel-transfer network. A Campus Hub should not casually store prepared food alongside general parcels. Any future
hub food handling requires its own approved operating model and facilities.
Operations workspace
Platform Operations → Compliance gains a Food view: Food Listings, Compliance Status, Open Concerns, Batch
Alerts, Seller Incidents, Affected Orders, Evidence, Escalations and Actions. Actions are permissioned and audited.
Launch validation
Before a production Eduvos rollout, confirm the student-food operating model with Eduvos and the relevant municipal
Environmental Health Service, including the practical route for applicable food-premises requirements. Final
consumer-facing terms and allocation of responsibility should receive South African legal review.
Locked food principle
Light on the student-facing surface; controlled underneath. Any Seller can enter the Food workflow, but Food
receives category-specific compliance guidance, seller obligations, structured disclosures, batch/time traceability, local
fulfilment controls, buyer protection and rapid incident response. Vossie communicates evidence and traceability rather
than making an unsupported promise that food is “safe.”

Promotions
Promotions are structured fields, not text embedded in listing titles. Initial promotion types: fixed price reduction,
percentage discount, bundle/deal. Seller enters regular price plus promotion terms/start/end; Vossie calculates and
displays the saving and automatically restores the normal price when the promotion ends. Price history is retained internally

Active | Draft | Under Review | Sold Out | Paused | Specials. Each row/card shows photo, title, current price,
stock/availability, views, orders, revenue and status, with Edit / Pause / Duplicate actions.
Seller storefront
Each seller receives a buyer-facing storefront with cover/profile assets, verified identity signal, rating, completed-order
count, campus, description, active categories and tabs such as All | category filters | Specials. The visual hierarchy is
therefore: Discovery Card → Listing Detail → Seller Storefront.
Asset handling
Listings support a cover image plus gallery. Vossie should validate file type/size, generate optimized thumbnails and
responsive derivatives, preserve an appropriate original, and serve media from controlled storage/CDN infrastructure.
Category-specific moderation rules apply. Buyer-facing imagery must not intentionally misrepresent the item being sold.
Discovery behaviour
The buyer sees simple top-level category tiles and progressive subcategory/filter chips. Structured search maps natural
queries into catalogue attributes—for example, “black hoodie medium” → Fashion / Clothing / Hoodie / Black / M; “Network+
tutor tomorrow” → Services / Tutoring / Networking / date availability; “calculator for three days” → Rentals / Academic /

Locked principle
One shared presentation system, category-aware transaction logic. Every listing looks recognisably Vossie, while
Food, products, Fashion, Services, Rentals and Digital expose only the controls needed for that transaction type.

27.2 Campus Transfer Network
Cross-campus fulfilment is a hub network, not a default long-distance trip by one student courier. Routing chooses the nearest
viable onward hub, considering direction toward destination, active routes, schedules, parcel compatibility, capacity, cost and
expected arrival - not geographic proximity alone.
Buyer fulfilment choice: where viable, checkout can present Vossie Campus Transfer, an integrated third-party courier option,
and other eligible collection/fulfilment methods. The buyer sees price/ETA information appropriate to each option.
A single shipment may contain multiple transfer legs. Each leg has a manifest and custody evidence. At every hub: arrival scan ->
manifest reconciliation -> custody recorded -> next viable leg -> outgoing manifest. Mismatches or missing packages create
exceptions rather than silent status changes.
Shipment lifecycle: Seller Ready -> Origin Hub Received -> Waiting for Transfer -> Manifested -> In Transfer -> Intermediate Hub
Received -> Next Transfer -> Destination Hub Received -> Local Delivery Ready -> Courier Collected -> Delivered.
The buyer sees one continuous shipment timeline/map with campus milestones. Hub and Operations users see the detailed legs,
manifests, custody holders, reconciliations and exceptions.
The production Campus Route Registry records origin, next hub/destination, distance, transfer method, operating days, cut-off,
expected duration, capacity, parcel classes, cost model and Active/Suspended state. Routing can select another permitted path
when a route is unavailable.
Vossie should not force inefficient multi-hop routing. Where the campus route is unreasonable, unavailable or materially inferior, an
integrated third-party shipment can be offered. Provider events map back into the Vossie timeline while the provider remains
authoritative for its own logistics events.
Local Courier and Campus Transfer Courier/Operator are distinct capabilities. Approval for local car delivery does not automatically
authorize inter-campus transfer work.
Prototype: selected campus nodes and routes are predefined and movement is simulated, while QR scans, manifests,
reconciliation, custody and shipment state transitions are functional.
27.3 Buyer Request Marketplace
Requests sit beside Listings. Search answers 'what supply exists now'; Request answers 'I need this - who can fulfil it?'. A request
is a demand-discovery route into the existing transaction engine, not a second commerce engine.
Flow: Request -> category-specific details -> matching -> eligible sellers notified -> structured seller offers -> buyer compares ->
accepts one offer -> normal Order/Booking/Rental -> payment -> fulfilment -> receipt/ledger/notifications.

Request creation and matching
Buyer Home/Search includes Can't find what you need? Request it. Initial request types are Product, Food, Service, Rental and
Digital. The existing taxonomy dynamically controls fields such as quantity, variant, condition, timing, duration, campus, fulfilment,
budget, dietary/allergen information, rental period and optional media.
Before broad matching, Vossie may surface compatible existing listings so buyers can transact immediately. If the buyer continues,
matching uses category/subcategory, campus, seller capability, availability, inventory/service type, fulfilment radius and seller
status. Requests are not indiscriminately broadcast to every seller.
Seller offers and buyer decision
Eligible sellers receive an Uber-like request card and may Respond or Dismiss. Responding creates a structured offer containing
price, timing/availability, relevant fulfilment or service terms and an optional concise note. Sellers do not see competing sellers' offer
prices, avoiding an uncontrolled visible bidding race.
The buyer receives real-time 'New offer' notifications and an Offers view containing the information needed to choose. Accepting an
offer locks/converts it into the existing transaction workflow; payment, ledger, protection, fulfilment, receipts and communications
are reused.
Request lifecycle and controls
Draft -> Open -> Matching -> Offers Received -> Offer Accepted -> Converted to Transaction -> Fulfilled -> Closed. Alternate
states include Expired, Cancelled, No Match and Moderation Hold. My Requests provides Active and Closed views; Seller Mode
adds For You, Responded, Won and Closed.
Requests cannot bypass marketplace controls. Food requests only reach sellers eligible for the relevant food category/compliance
state. Digital/academic requests remain subject to rights, academic-integrity and prohibited-content rules.
Incubation and Operations value
Unfulfilled and partially fulfilled requests become structured demand intelligence: category, campus, request volume, offer rate and
fulfilment rate. Incubation uses this to identify unmet demand and seller opportunities. Operations receives request
moderation/abuse tooling without manually controlling normal matching.
Prototype proof flow
Buyer requests a Network+ tutor tonight -> matching identifies eligible sellers -> Seller A sends a structured offer -> Buyer
receives the offer in real time -> Buyer accepts -> Vossie creates the booking -> sandbox payment -> seller confirmation ->
notifications/receipt/ledger update -> analytics records the conversion.
Locked combined principle
Courier capability is verified and mode-aware; cross-campus logistics is a custody-controlled hub network with optional third-party
fulfilment; and buyer Requests expose unmet demand while converting successful matches into the same trusted Vossie
transaction system.
