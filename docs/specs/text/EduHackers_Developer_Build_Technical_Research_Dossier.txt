1. Executive technical summary
Core recommendation: build a web/PWA MVP first, isolate payments and AI behind interfaces, and
instrument every key marketplace event from the start.
The EduHackers build should be researched as a modular marketplace platform, not as a simple listings application. The
product must coordinate identity, listings, protected payment states, delivery/pickup, messaging, disputes, trust progression,
events, gigs, rentals, digital products, AI moderation and Incubation Hub intelligence.
The recommended technical posture is boring and reliable for the MVP: a web-first installable PWA, a relational database,
typed APIs, strong role-based access control, a protected GitHub workflow and carefully isolated payment/AI integrations. A
native mobile app can be researched in parallel but should not block the MVP unless Eduvos requires app-store distribution.
The biggest build risk is not rendering screens. The hard parts are money movement, object-level authorization, data
privacy, dispute evidence, file security, moderation, marketplace liquidity and institutional governance. The architecture must
therefore be designed around boundaries, auditability and change.
Stack decision logic: use boring reliable tech for MVP, isolate risky integrations

2. Research status: what is known vs still
hypothetical
This document builds on the prior EduHackers marketplace research dossier. Several product choices are user-selected
hypotheses: integrated payments, held funds, 2% commission, campus-first discovery, student couriers, pickup points,
rentals, services with 30% deposits, AI compliance, Trusted Seller progression and Incubation Hub 30-day intervention

None of these are final implementation facts yet. The developer research must distinguish user experience intent from
technical/legal feasibility. For example, the app can show money as “held”, but actual held funds should be managed by a

The research must also avoid turning the system into a super-app too early. The MVP should prove the most valuable loop:
verified users, campus discovery, protected order state, fallback/request capture, demand signal generation and Incubation

3. Product modes the build must research
The marketplace is not one workflow. It contains different commercial modes that share identity, trust, messaging,
payments, dispute handling and analytics, but each has separate state rules. Treating all listings as one generic object will
create technical debt.
The research architecture should define a shared Listing core with mode-specific extensions. Product listings need stock
and condition. Services need availability, booking and 30% deposit logic. Rentals need deposits, return deadlines and
condition evidence. Digital products need licensing, download logs and file integrity. Food listings need ingredients,
allergens and category safety checks.

4. Delivery surfaces: web, mobile and desktop
install
The preferred research direction is PWA-first: build a responsive web app that can be installed on desktop and mobile. This
directly supports the user requirement for web + mobile + downloadable desktop experience while keeping one codebase
for the MVP.
MDN’s PWA guidance confirms that installable PWAs use a web app manifest and HTTPS; once installed, they can appear
and launch like a platform-specific app. Browser support varies across desktop and mobile platforms, so the user
experience must gracefully fall back to normal web access where installation is limited. [D1]
A native mobile app remains a serious phase-two option if camera scanning, push notifications, app-store discoverability,
reliable background location for couriers or native performance become decisive. Expo/EAS can produce Android and iOS
binaries from React Native projects and support internal distribution builds. [D2]

5. Recommended tech-stack direction
The build should optimise for speed, developer control, security and visibility during the Hack Jam. A TypeScript stack is
appropriate because it can share types between frontend, API contracts and validation. Next.js App Router route handlers
can create custom request handlers inside the app directory using standard Web Request/Response APIs. [D3]
Supabase is a strong research candidate because it provides Postgres, Auth, Storage, Realtime, Edge Functions, APIs and
Row Level Security in one platform. Supabase documentation states that every project includes a Postgres database with
Realtime capabilities, Auth, Storage and Edge Functions. [D4]
Postgres is the recommended data model foundation because the marketplace is relational: users, roles, listings, orders,
payments, disputes, evidence, events and Incubation records need strong consistency and queryability.

6. Tech-stack alternatives to research before

The recommended stack is not the only possible stack. The team should evaluate alternatives on team skill, cost,
compliance, payment support, identity integration, deployment speed and how easily the Hack Jam prototype can

no-code/low-code backend can prototype quickly but may be weaker for custom payment/dispute logic and security depth.

7. Reference architecture
The architecture should begin as a modular monolith: one deployment with clearly separated modules. This avoids
premature microservices while preserving boundaries. The payment, AI, notification and identity integrations should be
replaceable adapters, not hard-coded inside UI components.
The system should have separate bounded areas for identity, marketplace catalogue, orders/bookings/rentals, payments,
delivery/pickup, trust/safety, social discovery, analytics/demand intelligence and Incubation Hub support.

9. GitHub operating model
GitHub branch protection should be used so the main branch cannot be casually overwritten. GitHub protected branches
can require pull request reviews, required status checks, conversation resolution, signed commits, merge queues and push
restrictions. [D5]
The workflow should force traceability: every feature starts from research evidence or a product decision, becomes an issue,
gets a branch, receives a pull request, passes CI, receives review and is tested on a preview deployment before it is
considered done.

10. Branching and pull request rules
The Hack Jam team does not need a complex enterprise branching strategy. Use a lightweight trunk-style approach with
protected main, a develop branch if the team wants staging, and short-lived feature branches. All code changes should go
through pull requests.
The developer owner should not allow direct main pushes. This prevents last-minute breakage and gives
UX/Product/Research space to review whether the implementation still matches the evidence and design.

14. RBAC and object-level authorization
OWASP API Security Top 10 2023 identifies Broken Object Level Authorization as the first API risk and emphasizes
authorization checks for functions accessing data using user-supplied object IDs. [D9] This is directly relevant: a student
should never be able to modify another seller’s listing, payout state or dispute evidence by changing an ID in an API request.
Use both role-based access control and object ownership checks. Roles alone are not enough. A user may be a seller, but
they should still only edit their own seller profile, listings, order updates and evidence.

17. API response conventions and error
handling
API consistency matters because the project has many roles and modes. The frontend should not need to guess what a
failure means. Use stable response envelopes, typed error codes and field-level validation messages.
For sensitive flows, idempotency keys should prevent duplicate orders or duplicate payment-hold attempts if the user taps
twice or the network retries. Audit logs should record who initiated the action, what object was affected, and why.

21. Payment architecture research
The app should not directly hold student money. The internal domain model should represent a PaymentHold state, while a
regulated payment provider or banking partner manages authorisation, settlement, refunds and payouts. The prior
marketplace research already found that payment-processing fees may exceed the proposed 2% commission on some rails.
Payment research must determine the provider’s support for subaccounts, split payments, delayed release, partial refunds,
chargebacks, payout KYC, refund workflows and fee allocation. Crypto should remain later-phase research due to volatility,
compliance, refunds and disputes.

Appendix E. Final technical thesis
The developer build should prove that EduHackers can become an Eduvos student marketplace operating system, not
merely a digital notice board. The technical strategy is to keep the first build narrow, traceable and secure while preserving a
model that can expand into mobile, events, rentals, couriers, AI support and Incubation Hub interventions.
If the team can demonstrate verified users, campus-first discovery, protected order state, fallback
capture, demand intelligence and Incubation action in one reliable demo, it will have a stronger
technical story than a broader but shallow feature showcase.
