1. Executive summary
This dossier translates the developer-side architecture into a working collaboration system between the
Developer / Research Lead and the UX/UI workstream. The core recommendation is not a traditional handoff.
EduHackers should operate a dual-track workflow where research, UX flows, wireframes, technical state
machines, API contracts and GitHub implementation tasks are produced together. The team should avoid
building screens that do not have backend states, permissions, error states and acceptance criteria attached.
The output also includes low-fidelity example wireframes for Marketplace and Operations Platform screens.
These examples are not final visual design; they are system wireframes showing how buyer, seller, courier,
hub operator, transfer, moderation and incubation flows could connect.
Strategic recommendation
Use Miro for research/system thinking, Figma for wireframes/prototypes/components, and GitHub for feature
contracts, API definitions, implementation tasks, pull requests and decision logs. Every important flow should
move through a shared Feature Contract before build.
Evidence status
The workflow recommendations are grounded in official tool capabilities and product-engineering patterns.
Figma Dev Mode supports inspecting designs, ready-for-dev status, annotations and developer integrations;
Code Connect can map design components to code components. GitHub Issues and Projects link planning
directly to issues and pull requests. OpenAPI provides a standard interface description for REST APIs. WCAG
2.2 provides a widely used accessibility framework. These are used as references, not as claims that the
team already has paid seats or institutional integrations. [R1-R8]

2. Why this workflow matters for EduHackers
EduHackers is not a simple static marketplace. The system includes real-time seller dispatch, courier
dispatch, package custody, hub scanning, cross-campus transfers, role-based operations, seller capacity,
protected payments, wallet/withdrawals, disputes, and Incubation Hub intelligence. If UI/UX designs screens
in isolation, the prototype can look attractive but fail the moment a seller declines, a courier times out, a
package is rejected or a payment state changes.
The Developer and UX/UI Designer must therefore share one mental model: every visible state on screen
must be traceable to a backend state or event. Every backend state must be represented clearly enough that
the user knows what is happening, what they can do next, and what the platform is doing on their behalf.
The simplest rule: no screen is considered ready unless it has a matching state/API/event contract
and acceptance criteria.
What breaks without this workflow
 Designs can include buttons that do not map to any real backend transition.
 Developers can build endpoints that do not correspond to understandable user actions.
 Edge cases such as timeout, decline, hub rejection, courier unavailability and refund states get handled too
late.
 Marketplace trust can degrade because the UI does not explain protected payment, custody or verification
clearly.
 The team loses traceability between research evidence, product decisions, Figma screens and GitHub build
tasks.

The collaboration system should have three source-of-truth layers. Miro stores early research synthesis,
maps, service blueprints and unresolved decisions. Figma stores wireframes, prototypes, component states
and developer annotations. GitHub stores issues, API contracts, source code, tests and architecture decision
records. Large video files, reference PDFs and heavy design exports should not be treated as normal Git
history.
4. Developer ↔ UI/UX operating model
Figure 2. Research-to-build workflow loop. The workflow intentionally returns build findings back into research and design
rather than treating development as the end of the process.
The Developer / Research Lead and the UX/UI Designer should work as a pair during the first pass of every
high-risk flow. This does not mean both people do the same work. It means UX flow decisions and technical
state decisions are made close together. The Developer owns feasibility, state machines, APIs, data and
security boundaries. The UX/UI Designer owns the interaction model, screen flow, information hierarchy,
accessibility and Figma prototype. Both own the Feature Contract.
5. Feature Contract: the required handoff artifact

Page 5
Figure 3. Feature Contract matrix. Each row connects backend state, UI state, user action, API/event and next state.
The Feature Contract is the main bridge between Figma and GitHub. It should be short enough to maintain
but strict enough to prevent guessing. The contract should be attached to the GitHub issue and linked from
the relevant Figma frame or section.
Feature Contract fields
 Feature name and user goal.
 User role: buyer, seller, courier, hub operator, transfer operator, moderator, incubation staff, admin or
finance.
 Entry points and previous states.
 Backend states represented by the screen.
 Primary action and secondary actions.
 REST endpoints, WebSocket events and notifications involved.
 Permissions and role checks.
 Loading, empty, timeout, offline and error states.
 Analytics events and success metrics.
 Accessibility requirements and acceptance criteria.

7. Miro board structure
Miro should be used as the living systems board rather than as a file dump. Miro supports embedding
third-party content such as Figma, Google Docs/Sheets/Slides, Microsoft documents and Power BI content,
which makes it useful for connecting research context, flows and design references on one board. [R6]
Recommended Miro zones
 Research evidence: interviews, assumptions, validated/rejected hypotheses.
 Journey maps: buyer, seller, courier, hub operator, transfer operator, moderator, incubation staff.
 Service blueprint: frontstage user action, backstage system event, support process and data object.
 Architecture maps: marketplace, operations, real-time, payment, dispatch and custody flows.
 Open decisions: payment rules, campus hub rules, category-specific fulfilment, staff access and
legal/compliance questions.
 Feature backlog map: MVP, P1, research later, institutional decision required.
8. Figma file structure
Figma should be the UX/UI source of truth. Figma Dev Mode gives developers inspection,
ready-for-development status, annotations, version comparison and developer integrations; Code Connect
can map Figma components to production code components where the team later has the appropriate plan
and setup. [R1-R4]
Recommended Figma pages
 00 - Research references: linked Miro board, assumptions and key user journeys.
 01 - Wireframes: low-fidelity screens grouped by user role.
 02 - Marketplace prototype: buyer, seller and courier flows.
 03 - Operations prototype: hub, transfer, moderation, incubation, finance and admin flows.
 04 - Components: buttons, cards, inputs, status pills, timers, dispatch cards, QR scanner, map states.
 05 - Dev annotations: states, API names, error states and acceptance criteria.
 06 - Archive: rejected concepts and earlier versions.
Figma should not just be screens. It should also include component states. For EduHackers, important states
include available, busy, at capacity, paused, pending payment, hub rejected, awaiting repackaging, courier
assigned, in transit, transfer exception, investigation open and payout pending.

10. Design system and components

EDUHACKERS | DEVELOPER ↔ UI/UX WORKFLOW + WIREFRAME RESEARCH
Page 9
Figure 5. Design system pipeline. EduHackers should define tokens, components, states, patterns and API contracts before
polishing final UI.
The team should create a small design system early rather than drawing every screen manually. This reduces
inconsistency across Marketplace and Operations apps. The design system should include colour tokens,
typography, spacing, radius, elevation, status colours, motion rules, responsive breakpoints and reusable
components.
High-risk reusable components
 Dispatch request card with countdown, accept/decline and expired state.
 Status pill system for order, package, transfer, payment and reliability states.
 QR scanning panel with success, mismatch and offline fallback states.
 PIN entry with invalid PIN and retry limits.
 Map / live tracking panel with GPS lost and ETA updated states.
 Fee breakdown component with seller, courier, platform and processor fees.
 Wallet/withdrawal component with spendable, withdrawable and pending amounts.
 Operations table components with audit-friendly history and filter states.
11. Accessibility and inclusive interaction
WCAG 2.2 adds criteria relevant to this product, including focus visibility, target size, dragging movements,
redundant entry and accessible authentication. [R7-R8] EduHackers should not treat accessibility as
decoration. Timers, QR scanning, maps, live tracking, real-time alerts and complex dashboards create
accessibility risk if not planned from wireframe stage.
UX/developer accessibility rules
 Countdown timers must have clear text alternatives and should not be communicated only by animation.

 Critical actions such as accepting a request, confirming pickup, entering a PIN and releasing a payout
require large touch targets.
 Screens must handle keyboard/focus state for web and desktop clients.
 QR scanning must have fallback codes or manual entry where appropriate.
 Status cannot rely only on colour; use labels and icons/text.
 Maps must have text ETA/status alternatives.
 Forms must avoid requiring repeated entry of the same information when the system already knows it.
 Authentication and step-up verification must not rely on cognitive puzzles alone.

12. Marketplace wireframe examples
Figure 6. Marketplace app wireframes. These show buyer, seller and courier screens that the UI/UX Designer can convert
into polished Figma frames after the Developer confirms state and API contracts.
The marketplace app should support mode switching without creating separate identities. A student can be
Buyer-only after Eduvos verification, then activate Seller Mode or Courier Mode through progressive
verification. Each role unlocks additional screens and permissions.
Key marketplace screens to design
 Buyer home and campus-first discovery feed.
 Product/service listing and availability state.
 Fulfilment choice: hub pickup, courier delivery, seller delivery or category-specific direct food flow.
 Protected payment and fee breakdown.
 Seller incoming request with staggered batch countdown.
 Seller dashboard with category capacity and overall 25 active-order cap.
 Courier job offer with earnings, pickup/destination zone and ETA.
 Live delivery with tracking, messaging/calling and PIN handoff.
 Wallet and withdrawals with R50 withdrawal minimum and payout destinations.

 Transfer manifest: package count, scan reconciliation, origin/destination custody.

 Finance operations: payment exceptions, refunds, payouts and ledger adjustments.
 Admin configuration: campuses, hubs, role permissions, categories, fees, transfer windows and capacity
policies.
14. Detailed flow: seller dispatch
Seller dispatch should be designed as an Uber-style request mechanism adapted to campus commerce. The
matching engine ranks eligible sellers, sends staggered batches, locks the order atomically to the first valid
accepting seller and cancels other pending offers. UX must show urgency without causing confusion or
stress.

15. Detailed flow: hub intake and package rejection
Hub intake is a trust-critical workflow. The Hub Operator must scan the package QR, record condition and
either accept custody or reject the package before custody is accepted. If rejected, the seller gets a 24-hour
correction window, the buyer is notified, and the order remains protected but paused.

16. Detailed flow: courier delivery
Courier flows require realtime UI and shared courier capability across categories: live tracking, ETA,
order-scoped messaging/calling, earnings, status changes and proof of handoff. Product deliveries generally
flow through hubs, while food/perishables can use direct seller-to-buyer pickup when the category policy
requires it.
Proof model
 Package QR identifies the package or batch.
 Buyer one-time PIN confirms the correct recipient at final handoff.
 Hub scans establish physical custody.
 Condition checks record package state at custody transfer.

17. Detailed flow: cross-campus transfer
Cross-campus transfer uses scheduled hub-to-hub batches. Eduvos-approved transport is the primary
scheduled backbone; student transfer couriers can provide overflow or additional routes after opting into
transfer mode. The UI should hide unnecessary complexity from buyers but show enough status to build trust.
Transfer UX principles
 Buyer sees ETA and current stage: seller hub, in transfer, buyer hub, pickup/local delivery.
 Transfer courier sees package count and minimal package data only.
 Hub Operators scan every package at origin and destination.
 Manifest cannot depart until scan count matches the locked manifest.
 Destination reconciliation controls transfer completion and earnings release.
18. Detailed flow: Incubation intelligence
The Incubation module should not expose mysterious AI scores to sellers. Operations staff can see business
health indicators, demand signals, intervention suggestions and approved 30-day plans. Sellers receive
practical guidance, not internal scoring. The UX must separate analytics, advice and enforcement.
Developer and UX questions
 What data is safe and useful for Incubation staff?
 Which signals are aggregated rather than individual-level?
 How does staff approve an AI-suggested intervention?
 How does a seller see guidance without seeing a hidden score?
 How do we avoid turning analytics into surveillance?
19. API and event contract approach
OpenAPI defines a standard interface description for HTTP APIs that helps humans and computers
understand what a service can do without reading source code or inspecting network traffic. [R9] EduHackers
should use OpenAPI for REST contracts and a parallel event schema for WebSocket/realtime events.
Required contract outputs
 REST endpoint list with request/response schemas.
 WebSocket event list with payload schemas.
 Error codes and user-readable messages.
 Permission matrix for each endpoint/event.
 Analytics events mapped to user goals.
 Fixture/test data for UI development before backend is complete.

20. Workflow for wireframes
Wireframes should be produced in levels. Level 0 is the journey map. Level 1 is screen flow and state list.
Level 2 is low-fidelity layout. Level 3 is clickable Figma prototype. Level 4 is componentized high-fidelity
design. EduHackers should not jump to Level 4 until the state/API contract is stable.
Wireframe checklist
 Role and user goal visible on every frame.
 Entry and exit state named.
 Primary action and fallback action shown.
 Empty/loading/error/offline state planned.
 Notifications and realtime events noted.
 Accessibility notes attached for timers, maps, forms, QR and PIN.
 Linked GitHub issue created when ready for implementation.
21. What the UX/UI Designer should ask the Developer
 What backend states exist for this flow?
 Which states can arrive through WebSocket vs page reload?
 What errors/timeouts are possible?
 What can the user do when the API call fails?
 Which data is private and must not be shown to this role?
 What is the source of truth: database, payment provider, hub scan or location event?
 What is the acceptance test for this flow?
 Which analytics event tells us the design works?
22. What the Developer should ask the UX/UI Designer
 What is the user trying to decide on this screen?
 What information is essential before the user acts?
 How should urgency be communicated without creating stress?
 How does the user recover from a failed state?
 Which states need notifications?
 What should be hidden from this role?
 Which components can be reused?
 How will accessibility be tested?

27. Appendix: example feature contract template
Feature: Seller incoming request. User role: Seller. Goal: accept or decline a live buyer request quickly.
Entry state: SELLER_OFFERED. Primary action: Accept. Backend transition: atomic offer acceptance;
order locked; other offers cancelled. API: POST /seller-offers/{id}/accept. Realtime: seller.matched,
buyer.seller_found, seller_offer.closed. Permissions: seller must be verified, available, under capacity and
associated with listing. Error states: expired, already accepted by another seller, capacity exceeded, stock
unavailable, network offline. Acceptance criteria: two sellers tapping Accept simultaneously results in only
one successful lock.
